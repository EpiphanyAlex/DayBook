# ADR-0006：smart agent, dumb tools —— 工具的智能边界

- **日期**：2026-08-08
- **状态**：已接受
- **决策者**：@maintainer
- **相关**：[ADR-0002 AI 永不直接写入](./0002-ai-never-writes-directly.md)、[ADR-0003 Agent 运行时](./0003-agent-runtime-and-pluggable-backend.md)、[`docs/CONTEXT.md`](../CONTEXT.md)「smart agent, dumb tools」
- **2026-08-08 修订**：仓库转为公开：决策者署名改为非具名 handle；「附带决定：读取范围也要收窄」**去掉外部参考仓库出处，把「最小暴露 = AI 只读取任务需要的内容」这条原则直接写出**——**规定本身未变**。

## 背景

「smart agent, dumb tools」是当前 agent 工程里被广泛采纳的原则：**充分信任大模型的推理与规划能力，把工具做成简单的 executor**。它是对的，而且本项目应当采纳。

但这条原则有两种读法，其中一种会拆掉产品的护城河：

| | 读法 A | 读法 B |
|---|---|---|
| 工具**不做决策**（不判断该不该入库、要不要重试、是不是重复） | ✅ | ✅ |
| 工具**不做参数校验** | ❌ | ✅ |
| 数据层**不设非空/CHECK 约束** | ❌ | ✅ |
| 闸门交给 agent 自觉遵守 | ❌ | ✅ |

读法 B 曾在设计评审中被提出：MCP 工具只负责写库，校验留在工具之外。本 ADR 记录为什么采纳 A 而否决 B——**因为这个提议会再次出现**，而每次都要重新论证一遍太贵。

## 决策

**采纳读法 A。口号收窄为：dumb tools ≠ gullible tools —— 工具没有判断力，但有契约。**

### 归 agent 的（工具不碰）

- **推理**：这张截图上有几笔、每笔多少钱、商户是谁
- **规划**：先读哪个来源、要不要查记忆、什么时候算完
- **分类**：这笔归哪一类（[`CLAUDE.md`](../../CLAUDE.md) 约束 15 明确「LLM 做分类」）
- **判断**：这两条是不是同一笔（去重候选由代码给，判定由人做）

工具不判断「这笔该不该入库」「要不要重试」「是不是重复」。这些是 agent 的推理与代码控制流的事，工具里不写业务分支。

### 归工具与数据层的（不可移除）

- **参数校验**：`draft_transaction` 缺 `source_id` 或 `evidence_text` → 拒绝（`agent.tool_rejected`）
- **数据层约束**：草稿表的 `source_id` / `evidence_text` 为 `NOT NULL`；三元组与 `parse_attempts.reported_total_*` 的 all-or-nothing CHECK
- **写入范围锁死**：工具注册时声明写入目标表集合；与事实表的交集必须为空
- **读取范围锁死**：只读 ≠ 无限读（见下）
- **闸门**：草稿区隔离、证据链非空、总额校验无旁路、审计 append-only

**拒绝畸形输入不是智能，是类型。** 一个会拒绝无效参数的 executor 依然是 dumb executor——它没有在思考，它只是有契约。

### 附带决定：读取范围也要收窄

评审时发现 [01 Agent 运行时 §3.2](../prd/01-agent-runtime.md) 只声明了工具的**写入**目标表，只读工具一律标 `∅`。但**「只读」不等于「无限读」**：

- `query_memory` 若能列举全部规则，agent 就能把用户的**个人语境词表**整个拉进上下文（如「家里那笔 = 家庭支出」），而它对解析一张超市小票毫无用处
- `read_source` 应只能读被指派的那个来源，不能遍历

因此工具必须**同时声明读取范围**。这一条的原则是**最小暴露**：AI 只读取任务需要的内容。

## 理由

**核心论证：产品同时持有两个判断，而它们是同一个判断。**

1. **「agent 的输出需要人审」** —— [ADR-0002](./0002-ai-never-writes-directly.md) 的全部理由，审核界面存在的全部理由
2. **「agent 的输出需要工具挡」** —— 参数校验与数据层约束存在的理由

**若工具可以无条件信任 agent，则人审也无必要。** 反过来，若 agent 的输出需要人审，它同样需要工具挡住畸形输出。你不能同时相信「模型会把 168 读成 1680」和「模型不会漏填 `evidence_text`」。

**读法 B 的具体代价**：

- 拆掉 `evidence_text NOT NULL` ⇒ 闸门 2（证据链）失效 ⇒ 无证据草稿可以入库
- 让 agent 自行判断总额是否够接近 ⇒ 闸门 3 失效 ⇒ 唯一的自动纠错机制消失
- 于是产品退回 [`docs/PRD.md` §10](../PRD.md) 所述的同质化「AI 截图记账」赛道，证据链与总额校验也不再构成结构性差异

**「工具不写 DB 逻辑」单独否决**：工具不写库，那谁写？让 agent 发 SQL 就回到 [ADR-0003 §3](./0003-agent-runtime-and-pluggable-backend.md) 明令禁止的「通用执行任意 SQL 工具」——那是把权限边界彻底拆掉，不是简化。

## 后果

**得到**：

- agent 的推理空间没有被工具挤占——工具里没有业务分支，提示词和模型能力决定质量
- 越权在编译期不可表达：`DraftStore` 类型上根本没有写事实表的方法（见 [`.claude/rules/rust-tauri.md` §4](../../.claude/rules/rust-tauri.md)）
- 这条原则有了可引用的出处，下次被提议放松时不必重新论证

**付出**：

- 工具参数比「照单全收」啰嗦，agent 偶尔会因漏填参数吃一次 `agent.tool_rejected` 并重试
- 读取范围收窄意味着 agent 拿不到「全局视角」（例如列举全部记忆规则）。这是刻意的——它本来也不需要

**判据（供 review 时用）**：把工具清单列出来，逐个问——

1. 这个工具能不能让一条**未经人确认**的数据出现在 `transactions` 或 `items` 里？
2. 这个工具能不能读到**超出当前任务所需**的数据？

任一为「能」，即缺陷。
