## 背景

**视觉模型真的会把 168 读成 1680。**

账本与普通 AI 应用的差别在于错误的性质：摘要错一句话用户会笑一下，账本错一个数字用户信任就永久归零，而且**归零是不可逆的**——一旦用户开始「偷偷回去核对原始截图」，产品声称节省的时间就全部吐了回去，它已经失败了（[`docs/PRD.md` §7](../PRD.md) 成功标准）。

这不是「等模型变强就好了」的问题。模型能力提升只能降低出错概率，不能把账本错误变成可接受事件；本项目的结论是「使用 AI，但把它关在闸门后面」。这条决定不依赖任何竞品是否采用 AI（[`docs/PRD.md` §10](../PRD.md)）。

## 决策

**AI 永不直接写入账本。** 四道闸门，缺一不可，且都由代码强制而非由 agent 自觉遵守。

### 闸门 1：草稿区（两套表）

- agent 通过 MCP 工具能写的地方**只有两处**（2026-08-10 说全）：
  - **业务实体输出 → 只能进 `draft_*` 表**（`draft_transactions`、`draft_items`…）
  - **协议与对账元数据 → 只能写当前 attempt 那一行的六个白名单列**（`parse_attempts` 的 `reported_total_*` 四列 + `reported_item_count` + `unparsed_note`，见 [`docs/prd/00-foundation.md` §3.6](../prd/00-foundation.md)）
- **其余每一张表、每一列都不可达**；事实表（`transactions`、`items`）只能由**人工确认动作**写入。
- **任何绕过草稿区的写入路径都是缺陷**，包括「agent 直接调用确认命令」这种形式上合规、实质上绕过的路径。
- 工具的写入范围锁死在实现层（见 [ADR-0003](./0003-agent-runtime-and-pluggable-backend.md)「工具权限」）：**不得提供通用的「执行任意 SQL」类工具**。

> 本条原文只写「只能写 `draft_*` 表」。**那在 2026-08-10 引入 `report_source_total` 的落点与 `complete_source` 之后就不准了**——它们确实要写库，只是写的不是账目。**闸门 1 的实质从来不是「只有一张表可写」，是「agent 产出的任何东西都不能未经人确认就成为事实」**，所以按「写的是什么」分档比按「写哪张表」更准：**账目走草稿区，元数据走 attempt 白名单，事实表谁也够不着。**

**「工具集」指的是 agent 实际拿得到的那一套，不是我们注册的那一套**（2026-08-10 补）。本应用注册的 MCP 工具只是其中一部分——agent CLI 自带内置工具（执行命令、读写文件），足以绕过 MCP 直接打开 SQLite 写事实表。**因此闸门 1 的前提是子进程以「密封启动配置」启动，并且有效工具集经过实测**，规格与验收见 [`docs/prd/01-agent-runtime.md` §3.7](../prd/01-agent-runtime.md)。**只遍历自己的工具注册表的测试证明不了闸门 1。**

### 闸门 2：证据链

- 每一条草稿**必须**挂载来源：`source_id`（哪张截图 / 哪个文件 / 哪段口述）+ **`evidence_text`**（agent 声称自己读的是哪一段）。
- 审核界面**必须**把**来源原件**与解析结果**并排**呈现，`evidence_text` 作为定位锚点同屏显示。
- **无证据的草稿不得入库**——这条在数据层用非空约束强制，不靠 UI 自觉。

**证据是不可变原件，`evidence_text` 是抽取声明**（2026-08-10 收紧）。两者此前都被称作「原文」，但它们的可信性不同级：截图是导入时逐位落盘、之后谁也不改的字节；`evidence_text` 是**同一次模型输出的一部分**，与被核对的金额同源。模型把 168 读成 1680 时，它同样可能把 `evidence_text` 写成「1680」——**两者自洽，却一起错**。所以 `evidence_text` 只能当作「原件上的哪个位置」的指针，**不能当作核对基准**。

由此得到一条硬要求：**审核界面上，来源原件必须是可见的**（截图渲染出来 / `utterance` 的转写文本原样显示），不能只呈现 agent 抄录的那个字符串。作用是把用户的心智负担从「我要信任这个 AI 解析对不对」换成「我扫一眼原件，对得上就过」——**前提是他看的确实是原件**。

### 闸门 3：总额交叉校验

- 从一个来源拆出的条目，其**合计**只与一条**覆盖当前不可变来源全部适用交易的声明合计**核对。来源可以是任意 viewport 截图；边界是导入后不再改变的证据字节，不是截图背后的整页、整月或其他分页。
- 不符时**显式报警**；`kind = file` **阻止批量入库**——不是警告一下让用户自己判断，是挡住。`kind = utterance` 的放行由 `confirmation_policy` 决定，与对账结果无关（见下文「第四态 `not_applicable`」与「两个维度」），代价是那道人工闸门的 UI 硬要求，**且 `failed` 时差额必须与确认按钮同屏**。

**这是唯一能在无人工介入下捕获错误的机制，因此它的优先级高于解析准确率本身。** 一个能自己发现「我算出来的 12 笔加起来是 1839.20，但截图底部写着 1847.20」的系统，比一个准确率高 2% 但不会自查的系统可靠得多。

**基准是「声明合计」，不是「账户余额」**（2026-08-09 修订）：交易合计 ≠ 期末余额。要用余额做校验，至少需要期初余额、期末余额与每笔的方向，三者缺一不可，而截图上通常只有其中一个数字。来源上只印余额、没印合计时，正确结果是 `unavailable`（[`docs/prd/03-review.md` §3.3](../prd/03-review.md)），不是凑一个数。账户余额推演本身是 v1 非目标（[`docs/prd/04-transactions.md` §2](../prd/04-transactions.md)）。

**claim 的范围必须先成立**（2026-08-30 修订）：类型正确不等于 scope 正确。M0 中 `expense_total` 必须覆盖当前来源全部支出，`income_total` 覆盖全部收入，`net_change` 覆盖全部收入与支出；月度 / 周期合计若覆盖 viewport 外交易，分页合计若覆盖其他页，按日 / 分类 / 单笔语义 / 子组合计若只覆盖局部，全部为 **scope-invalid**，不得调用 `report_source_total`。来源同时出现多条局部 claim 时也不得任选一条；有效来源级 claim 与 invalid decoy 若恰好 amount/currency/kind 相同，现有四列无法审计身份，M0 保守地都不报告。`总共` / `一共` / `合计` / `总计` / `TOTAL` 只是候选信号，不能证明范围。

**M0 不为范围资格新增生产字段或多 claim 表。** 没有独立 OCR 的代码无法从图像字节证明 agent 选中的行覆盖了什么；因此生产侧由提示词收窄，正式评测用 bounded `candidateClaims` 保证三元组唯一，再固定 eligible claim 的 amount/currency/kind 身份，并强制 `scope-invalid` 成功报告数为 0（错报同源 decoy 也计入）（[07 评测 §3.4](../prd/07-eval.md)）。未满足资格时不报告，不能为了启动闸门而使用一个错误基准。多 claim schema 仍留 [00 地基 §5](../prd/00-foundation.md) R7 到 M2。

**合计必须带类型**（2026-08-10 修订）：一个裸数字表达不了「本期消费合计」「本期收入合计」「净变动」的差别，而它们对应**三条不同的等式**——把收入行算进「消费合计」，校验会稳定地错。因此声明合计**连类型一起存**（`reported_total_kind`，取值集与逐条等式见 [`docs/prd/00-foundation.md` §3.6](../prd/00-foundation.md) 与 [`docs/prd/03-review.md` §3.3](../prd/03-review.md)）；**类型判不出来时，正确结果是 `unavailable`**，不许挑一条等式试试看。这与「余额不当合计用」是同一条原则：**基准的语义不确定，就不是基准。**

**第四态 `not_applicable`**（2026-08-10 新增，2026-08-30 补 scope）：**「当前来源没有 scope-valid 合计」与「文件本该有却取不到」必须分开。** 一段未说出 current-source 全覆盖 claim 的口述没有可用机器基准，而一张账单截图取不到合计，说明要么 agent 漏读了、要么这张图不完整——前者是口述常态，后者是一个信号。把两者都塞进 `unavailable` 会让语音路径永远被批量确认挡住（那是产品的核心动作），也会让截图路径的真实信号被口述噪声淹没。

**但「能不能对账」与「能不能批量确认」是两个维度，不是一个枚举的两个值**（2026-08-10 同日拆开，2026-08-30 补 scope 限定）：口述里若明确说出一条覆盖整段全部适用交易的来源级合计，对账可做；一张只印一笔、没有合计的截图则相反——对账不适用，却**不该因此获得批量放行**。因此判定结果是一对：

```
reconciliation_status:  passed | failed | unavailable | not_applicable
confirmation_policy:    reconciled_batch | user_attested_batch | single_only
```

**真正放行批量确认的是 `confirmation_policy`。** `user_attested_batch` 不是旁路，因为它换了一道人工闸门：**代价是审核界面必须把来源原件全文与全部拆分结果并排展示**——用户按下确认前看到的是「我说的这段话」和「系统拆出来的 N 条」，那一次确认就是校验动作本身。这条 UI 要求是该策略成立的前提，不是加分项（[`docs/prd/03-review.md` §3.3](../prd/03-review.md)）。**`file` 类来源永远拿不到 `user_attested_batch`，也不得判为 `not_applicable`。** 理由不是「截图理论上一定有合计」，而是**我们手上唯一的信号（合计字段为空）对应三种完全不同的现实**：原件结构性没有合计、agent 漏读了、用户截图时裁掉了底部。**从「没读到」反推「本来就没有」，会把漏读伪装成正常**——而漏读正是闸门 3 存在的全部理由。要支持 `file` 的 `not_applicable`，需要一个**独立于字段为空**的适用性信号，不能从缺失反推（[`docs/prd/03-review.md` §3.3](../prd/03-review.md)）。

**校验的对象是「一次解析尝试」，不是「一个来源」**（2026-08-10 修正）：声明合计与草稿都是**某一次 agent 解析的输出**，两者必须同生共死。放在来源上会让它们脱钩——第一次尝试超时后草稿按尝试作废、合计却留着；一个来源被成功解析两次时，按来源求和会把两次的输出混在一起。因此**合计存在 `parse_attempts.reported_total_*`，校验的入参是 `attempt_id`**（[`docs/prd/00-foundation.md` §3.6](../prd/00-foundation.md)）。**原件属于来源，读出来的东西属于尝试。**

### 闸门 4：append-only 审计日志

- 每一次 agent 写入、每一次人工修改都留一条「**谁 / 何时 / 把什么改成了什么**」。
- 审计表**只追加，不更新、不删除**。

## 理由

**为什么不是「让 AI 写，但标记为未确认」**：状态字段是软约束。一旦事实表里同时存在已确认与未确认记录，所有下游查询（回顾、统计、导出）都要记得过滤，漏一处就把 AI 的猜测当成了事实。两张表是硬约束，漏不掉。

**为什么证据必须精确到原文片段而不只是截图**：只挂截图，用户审第 7 条时要自己在图上找到第 7 行——审核成本随条目数线性增长，40 笔 30 秒的目标做不到。

**为什么总额校验比准确率重要**：准确率是概率，交叉校验是确定性检查。产品的可信度不能建立在概率上。这与产品对用户的整体主张同构——**把「你信不信 AI」换成「跑一下就知道」**，也正是 [`CLAUDE.md`](../../CLAUDE.md)「验收标准必须尽量写成可执行的命令」那条纪律的同源理由。

**为什么审计日志必须 append-only**：可更新的审计日志不是审计日志。

## 后果

**得到**：

- 用户可以在不信任模型的前提下使用模型
- 错误在入库前被拦截，而不是在三个月后对账时才发现
- 任何一条数据都能回溯到「哪张截图的哪一行」

**付出**：

- 数据层要维护 `draft_*` 与事实表两套结构，字段变更要同步改两处
- 每次导入都要多一步人工确认——**这不是缺陷，是产品形态本身**（低频、重型、有仪式感，[`docs/PRD.md` §1](../PRD.md)）
- 无法提供「全自动记账」这种听起来很美的能力。竞品可以吹，本产品不能

**对实现的硬性要求**（违反即缺陷）：

1. 事实表没有任何 agent 可达的写入路径
2. 草稿表的 `source_id` 与 `evidence_text` 字段非空
3. 批量确认命令只按 `confirmation_policy` 放行：`single_only` 返回错误且不提供 `--force`；`kind = file` 对账不符/无法校验必为 `single_only`，`utterance` 只能经 `user_attested_batch` 的整段原文人工背书放行（[03 审核 §3.3](../prd/03-review.md)）
4. 审计表无 `UPDATE` / `DELETE` 语句
5. **agent 子进程的有效工具集经过实测**，而不只是「我们没注册越权工具」（2026-08-10 新增，见闸门 1 补注）
6. **审核界面呈现来源原件本身**，不是只呈现 agent 抄录的 `evidence_text`（2026-08-10 新增，见闸门 2 补注）
7. **agent 起草的原始值不可变**：人在审核时的修改不得覆盖掉「AI 当初写的是什么」。它是审计的溯源答案，也是 eval **被评分的那一侧**（不是 eval 的真值——真值是人工标注的期望条目集合，见 [`docs/prd/07-eval.md` §3.2](../prd/07-eval.md)）（[`docs/prd/00-foundation.md` §3.6](../prd/00-foundation.md) `drafted_json`、[`docs/prd/07-eval.md` §3.2](../prd/07-eval.md)）
8. **M0 的 `report_source_total` 只接受 current-source 全覆盖 claim**：scope-invalid 合计不得为了提高可获得率而进入基准；关键词不能强制报告。生产仍是单 claim 四列，正式评测按 expected claim 身份判定的 scope-invalid 成功报告数必须为 0（[`docs/prd/00-foundation.md` §3.6](../prd/00-foundation.md)、[`docs/prd/07-eval.md` §3.4](../prd/07-eval.md)）
