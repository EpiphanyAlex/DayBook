## 背景

**视觉模型真的会把 168 读成 1680。**

账本与普通 AI 应用的差别在于错误的性质：摘要错一句话用户会笑一下，账本错一个数字用户信任就永久归零，而且**归零是不可逆的**——一旦用户开始「偷偷回去核对原始截图」，产品声称节省的时间就全部吐了回去，它已经失败了（[`docs/PRD.md` §7](../PRD.md) 成功标准）。

这不是「等模型变强就好了」的问题。**海外开源记账工具集体回避 AI** 可以佐证这道坎是真实的：Firefly III 的官方立场就是「不要黑盒机器学习」（[`docs/PRD.md` §10](../PRD.md) 竞品调研）。他们的结论是「那就不用 AI」；本项目的结论是「用，但把它关在闸门后面」。

## 决策

**AI 永不直接写入账本。** 四道闸门，缺一不可，且都由代码强制而非由 agent 自觉遵守。

### 闸门 1：草稿区（两套表）

- agent 通过 MCP 工具**只能写 `draft_*` 表**（`draft_transactions`、`draft_items`…）。
- 事实表（`transactions`、`items`）只能由**人工确认动作**写入。
- **任何绕过草稿区的写入路径都是缺陷**，包括「agent 直接调用确认命令」这种形式上合规、实质上绕过的路径。
- 工具的写入范围锁死在实现层（见 [ADR-0003](./0003-agent-runtime-and-pluggable-backend.md)「工具权限」）：**不得提供通用的「执行任意 SQL」类工具**。

### 闸门 2：证据链

- 每一条草稿**必须**挂载来源：`source_id`（哪张截图 / 哪个文件）+ **原文片段**（图上那一行的文本）。
- 审核界面**必须**把原文与解析结果**并排**呈现。
- **无证据的草稿不得入库**——这条在数据层用非空约束强制，不靠 UI 自觉。

作用是把用户的心智负担从「我要信任这个 AI 解析对不对」换成「我扫一眼原文，对得上就过」。后者是几百毫秒的事，前者是无解的。

### 闸门 3：总额交叉校验

- 从一个来源拆出的条目，其**合计**必须与**该来源自身印着的声明合计**核对（账单底部那一行 Total）。
- 不符时**显式报警并阻止批量入库**——不是警告一下让用户自己判断，是挡住。

**这是唯一能在无人工介入下捕获错误的机制，因此它的优先级高于解析准确率本身。** 一个能自己发现「我算出来的 12 笔加起来是 1839.20，但截图底部写着 1847.20」的系统，比一个准确率高 2% 但不会自查的系统可靠得多。

**基准是「声明合计」，不是「账户余额」**（2026-08-09 修订）：交易合计 ≠ 期末余额。要用余额做校验，至少需要期初余额、期末余额与每笔的方向，三者缺一不可，而截图上通常只有其中一个数字。数据层因此只建了 `declared_total_minor` / `declared_total_currency` / `declared_total_evidence_text` 三列（[`docs/prd/00-foundation.md` §3.6](../prd/00-foundation.md)），**没有登记「这个数是合计还是余额」的字段**——把余额当合计填进去，校验会稳定地错。来源上只印余额、没印合计时，正确结果是 `unavailable`（[`docs/prd/03-review.md` §3.3](../prd/03-review.md)），不是凑一个数。账户余额推演本身是 v1 非目标（[`docs/prd/04-transactions.md` §2](../prd/04-transactions.md)）。

### 闸门 4：append-only 审计日志

- 每一次 agent 写入、每一次人工修改都留一条「**谁 / 何时 / 把什么改成了什么**」。
- 审计表**只追加，不更新、不删除**。

## 理由

**为什么不是「让 AI 写，但标记为未确认」**：状态字段是软约束。一旦事实表里同时存在已确认与未确认记录，所有下游查询（回顾、统计、导出）都要记得过滤，漏一处就把 AI 的猜测当成了事实。两张表是硬约束，漏不掉。

**为什么证据必须精确到原文片段而不只是截图**：只挂截图，用户审第 7 条时要自己在图上找到第 7 行——审核成本随条目数线性增长，40 笔 30 秒的目标做不到。

**为什么总额校验比准确率重要**：准确率是概率，交叉校验是确定性检查。产品的可信度不能建立在概率上。这与产品对用户的整体主张同构——**把「你信不信 AI」换成「跑一下就知道」**，也正是 [`CLAUDE.md`](../../CLAUDE.md)「验收标准必须尽量写成可执行的命令」那条纪律的同源理由。

**为什么审计日志必须 append-only**：可更新的审计日志不是审计日志。

## 后果

**得到**：

- 用户可以在不信任模型的前提下使用模型
- 错误在入库前被拦截，而不是在三个月后对账时才发现
- 任何一条数据都能回溯到「哪张截图的哪一行」

**付出**：

- 数据层要维护 `draft_*` 与事实表两套结构，字段变更要同步改两处
- 每次导入都要多一步人工确认——**这不是缺陷，是产品形态本身**（低频、重型、有仪式感，[`docs/PRD.md` §1](../PRD.md)）
- 无法提供「全自动记账」这种听起来很美的能力。竞品可以吹，本产品不能

**对实现的硬性要求**（违反即缺陷）：

1. 事实表没有任何 agent 可达的写入路径
2. 草稿表的 `source_id` 与原文片段字段非空
3. 批量确认命令在总额校验未通过时返回错误，不提供 `--force` 之类的旁路
4. 审计表无 `UPDATE` / `DELETE` 语句
