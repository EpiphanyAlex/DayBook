# ADR-0005：语音与系统集成——v1 零 Swift，sidecar 推迟到 v1.1

- **日期**：2026-08-06
- **状态**：**提议中**（v1 的「零 Swift」部分已由产品决定；v1.1 的 sidecar 形态待 v1 交付后复核）
- **决策者**：@maintainer
- **相关**：[ADR-0001 本地优先桌面平台](./0001-local-first-desktop-platform.md)、[`docs/PRD.md` §6](../PRD.md)
- **2026-08-17 修订**：随 [05 事项](../prd/05-items.md) v0.8 澄清 §3：系统听写可以形成事项的新建/修改指令，**但不执行最终确认、不让 agent 直接写事实**；交易金额与事项 update 的目标/字段差异仍须视觉审核。v1 零 Swift与 sidecar 分期不变。

## 背景

有三处系统能力在 macOS 上是原生一等公民，但在 Tauri + Rust 里拿不到：

1. **语音转写**——用户「一句话丢一堆事项进 backlog」是事项模块的主要输入方式。
2. **照片库读取**——用户的截图大多躺在系统照片库里，PhotoKit 是唯一的正规访问途径。
3. **弱信号采集**——日历、屏幕使用时间等。

同时有两条约束限制解法：

- **数据不出本机**（[ADR-0001](./0001-local-first-desktop-platform.md)）：语音转写不能调云端 API，音频不出本机。
- **2026-08-08 修订**：仓库转为公开，决策者与「状态」行的署名改为非具名表述。**决策内容与状态（提议中）未变。**
- [ADR-0001](./0001-local-first-desktop-platform.md) 选择了 Tauri 而非 SwiftUI，意味着这些能力要通过某种进程边界拿。

## 决策

### 1. v1 写零行 Swift

**语音**：v1 使用 **macOS 系统听写**——用户在输入框内自行触发（连按两下 `Fn`），文本直接落进输入框。应用不写任何代码，不申请任何权限。

**照片库**：v1 不读照片库。用户从访达或照片 app 里**拖拽**截图进应用窗口。

**弱信号采集**：v1 完全不做（[`docs/PRD.md` §6](../PRD.md) 非目标）。

### 2. v1.1 引入 Swift sidecar

形态是**无 UI 的独立命令行二进制**，由 Tauri 侧 spawn，通过 stdio 通信：

| sidecar | 能力 | 规模估计 |
|---|---|---|
| 照片库读取 | PhotoKit：按时间范围列出截图、导出到应用目录 | 约 150 行，单个 `.swift` 文件 |
| 语音转写 | SpeechAnalyzer：本地转写，音频不出本机 | 约 150 行，单个 `.swift` 文件 |

**约束**：单个 `.swift` 文件、`swiftc` 一行编译、命令行可验证、无 UI、无 `.xcodeproj`。

### 3. 系统听写用于下指令，不替代审核确认

这条不分版本：语音先由系统听写变成输入框里的文字，随后与键入文本走同一条来源与草稿链路。

- 可以说「牙医改到周四下午三点」或「牙医 3:15 才开始，看了 90 分钟」，让 agent 起草事项的新建/修改；
- agent 的目标匹配、字段解释与 before/after 差异必须显示在审核界面，经人确认后才写 `items`；
- 语音不能执行最终确认，不能绕过草稿区，也不能取代交易审核里的精确行定位；
- 「第 7 条金额改成 168」这类密集财务审核仍走键盘与行内编辑（[`docs/PRD.md` §5.1](../PRD.md)）。

边界不是「语音不能表达修改意图」，而是**语音表达的意图仍需视觉审核，AI 永不直接改事实**（[ADR-0002](./0002-ai-never-writes-directly.md)）。

### 4. 弱信号采集的前置条件（未来做时必须满足）

- **默认全关**，逐项授权，可随时关闭
- 采集结果**只留本机**
- **窗口标题等高敏数据必须在 UI 上明示其敏感性**
- 应当接 [ActivityWatch](https://github.com/activitywatch/activitywatch)（开源、本地优先、可写自定义 watcher）而**不是自己造**（[`docs/PRD.md` §10](../PRD.md)）

## 理由

**为什么 v1 零 Swift**：M0 要验的最大未知数是「视觉模型读真实银行与支付账单截图到底准不准」（[`docs/PRD.md` §9.1](../PRD.md)）。系统听写与拖拽导入都能零成本满足 v1 需求，写 sidecar 只会推迟撞上那个真问题的时间。

**为什么 sidecar 而不是 Rust FFI 直调 Objective-C**：PhotoKit 与 SpeechAnalyzer 的 API 都重度依赖 Swift 并发与回调，从 Rust 通过 `objc` crate 桥接的代码量与脆弱度远高于写 150 行 Swift。

**关于「Swift 的 AI coding 体验差」**：这个论断真正卡在验证循环——`.xcodeproj` 是巨大 XML、`xcodebuild` 反馈慢、SwiftUI 运行时问题要肉眼看模拟器。**本决策约定的 Swift 面积恰好完全避开全部三点**：单文件、`swiftc` 一行编译、命令行验证、无 UI。这是「sidecar 可以接受、SwiftUI 全家桶不可接受」的分界线。

**为什么系统听写够用**：v1 的语音输入场景是「一句话批量新建或修改几件事项」——用户当场能看到转写文本，随后还会看到目标匹配与字段差异再确认。事项时间既可以精确到分钟，也可以只是日期范围；系统听写的错误由原文可见 + 草稿确认兜底，不依赖“事项天然粗粒度”这个已被推翻的前提。

## 后果

**得到**：

- v1 的技术面完全收敛在 Tauri + Rust + React 里，不需要任何 Xcode 工具链
- 语音与照片库的能力缺口有明确的补齐路径，不是死胡同
- 音频永不出本机这条承诺在两个版本里都成立（系统听写由 macOS 本地完成）

**付出**：

- v1 的语音输入依赖用户知道「连按两下 `Fn`」——产品要在 UI 上提示
- v1 用户要手动从照片库拖文件，比「应用自己列出最近的截图」多几步
- v1.1 引入 Swift 后，构建流程要加一步 `swiftc` 与二进制签名/公证

## 状态说明

**为什么这份 ADR 是「提议中」而非「已接受」**：v1 的「零 Swift」部分已经拍板、无异议；但 v1.1 的 sidecar 形态（尤其 SpeechAnalyzer 的实际转写质量、PhotoKit 权限弹窗对「无远程服务端、无遥测」姿态的影响）**在 v1 跑起来之前无法验证**。等 v1 交付、真实使用暴露出语音与照片库的实际痛感后，再把本 ADR 改为「已接受」或另立新 ADR 修订。

**在此之前，本 ADR 的 §1（v1 零 Swift）与 §3（系统听写用于下指令、最终变更仍须视觉审核）按已决执行。**
