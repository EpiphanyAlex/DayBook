## 背景

产品要同时承载两类数据：**钱**（有外部原件、不容忍模糊、有交叉校验的可能）与**事项时间**（系统不能被动观测，但用户可以用口述/文字明确提供计划与结果，粒度可精确到分钟也可只是日期范围）。它们共享一条时间轴，但证据来源与容错要求相差一个量级：没有用户陈述时不得从计划、点击时刻或系统活动编造结果。

同时，[ADR-0002](./0002-ai-never-writes-directly.md) 要求草稿与事实分表、每条草稿挂证据、审计日志 append-only——这些都要在数据层落地成硬约束，不能靠应用层自觉。

**多币种是常规情况，不是边缘情况。** 解析能力天然不区分币种（[`docs/PRD.md` §3.1](../PRD.md)——它不认识具体格式，也就无从被币种局限），用户账户里出现几种货币只取决于他自己的生活。因此「外币消费按当时汇率折进本位币」必须是主路径，不能做成事后打的补丁。

## 决策

### 1. SQLite 是唯一事实源

- 用 **`rusqlite`**（bundled）在 Rust 侧访问，不引入 ORM，不用 `tauri-plugin-sql`（会破坏架构分层——前端不应直接触及 SQL）。
- **截图证据存旁边的普通目录**，数据库只存路径与元数据。理由：二进制大对象放进 SQLite 会让数据库文件迅速膨胀到难以备份，而普通目录用户能自己翻看。
- 另提供**纯文本导出**，作为「用户随时能带着数据走」的兜底。
- 数据库文件放在**用户看得见、能备份**的位置；**不放 iCloud Drive**——iCloud 的按需下载与文件替换会损坏 SQLite（WAL 与主文件不同步）。

### 2. 金额一律以整数存储最小货币单位

**任何位置禁止用浮点数表示金额，包括中间计算与 IPC 传输。**

- Rust 侧用 `i64`。
- **IPC 上金额与汇率是十进制字符串**，TS 侧在桥接层显式解析成安全整数（2026-08-10 改，见下）。
- **不是格式化后的字符串**（`"1,234.50"`），是**最小单位整数的十进制写法**（`"123450"`）——两者完全不同，别混。

**为什么 IPC 不直接传 JSON 数字**（2026-08-10 补）：JS 的 `number` 是 IEEE-754 双精度。Rust 的 `i64` 序列化成 JSON 数字后，`JSON.parse` 会把超过 `2^53 − 1` 的值**悄悄舍入**——没有异常、没有告警。而这个值不是假想的：**agent 把截图上的数字读错成 20 位就会产生它**，正好是本 ADR 与 [ADR-0002](./0002-ai-never-writes-directly.md) 最要防的那类错误，却会以「安静地少了 1」的形式通过。

字符串边界把这条静默路径变成一次响亮的错误：Rust 序列化前校验范围、TS 解析时再校验一次，超出返回 `data.amount_out_of_range`。**TS 内部仍用 `number`**——`≤ 2^53` 的整数在双精度里是精确的，而前端本来就不做金额累加（汇总一律由 Rust 给出）。范围不变式与迁移到 `bigint` 的后路见 [`docs/prd/00-foundation.md` §3.4](../prd/00-foundation.md)「金额怎么过 IPC」。

- 金额在 TS 侧另加分支类型（branded type）标记为「最小单位整数」，防止和「主单位」混用——**它挡的是单位混用，挡不住精度**，两件事各由一个机制负责。
- 只在**显示层**做「最小单位 → 主单位」的格式化，且格式化函数是唯一允许出现除法的地方。
- 具体的 ❌/✅ 代码对照见 [`.claude/rules/money-and-data.md`](../../.claude/rules/money-and-data.md)。

**「最小货币单位」不等于「分」**（2026-08-10 补）：每种货币的最小单位由 **ISO 4217 的 minor unit exponent** 决定——多数币种是 2（1 元 = 100 分），但 **JPY / KRW 是 0**（最小单位就是 1 日元），**KWD / BHD / JOD 是 3**。因此：

- **`amount_minor` 的含义随 `currency` 变**，读它必须同时读币种，单看数字没有意义。
- **格式化除以 10^exponent，不是除以 100。** 全仓库不得出现写死的 `/ 100`。
- exponent 是**币种的属性，不是行的属性**——不入库，由代码里一张 ISO 4217 表给出；表里没有的币种返回 `data.unsupported_currency` 并拒绝写入（具体规则见 [`docs/prd/00-foundation.md` §3.4](../prd/00-foundation.md)）。

**为什么不给每行存一个 exponent**：同一币种的 exponent 是全局常量，逐行存等于允许两行 `CNY` 有不同的 exponent——那是一个只会被写错、不会被用到的自由度。

### 3. 多币种三元组

每笔交易同时存三个值：

| 字段 | 说明 |
|---|---|
| **原币金额 + 币种** | 用户实际付出的那个数字，与截图上的完全一致 |
| **本位币金额 + 本位币种** | 按当时汇率折算的结果，以及折算到的是哪种本位币 |
| **当时汇率** | 折算所用的汇率本身 |

**本位币种逐笔存储**，因为本位币可切换（见文末「原『已知未决』已关闭」）。三个值加上各自的币种标识，构成一条自足的记录——脱离任何全局设置也能解释清楚。

- **不得只存换算后的结果**——那样就永远无法回到「截图上写的到底是多少」，证据链断裂（[ADR-0002](./0002-ai-never-writes-directly.md) 闸门 2）。
- **不得在录入时要求用户手算**——汇率折算是产品该做的事。
- 汇率同样以整数存（定点数，存放大若干倍后的整数 + 明确的标度），不用浮点。
- 单币种交易（本位币 = 原币）也走同一套三元组，汇率为 1，**不设特例分支**。

**汇率存的是「主单位对主单位」的那个数**（2026-08-10 定死）：`rate_ppm` = 「1 单位原币 = 多少本位币」× 1_000_000，两边都按**主单位**计。这样存的理由是**它就是账单上印的那个数、也是用户会手填的那个数**——存别的形式等于让证据链在汇率这一项上断掉。

代价是**换算公式必须带 exponent**，不能直接乘：

```
base_amount_minor = round_half_even(
    amount_minor × rate_ppm × 10^exp(base_currency)
    ÷ (1_000_000 × 10^exp(currency))
)
```

两边 exponent 相同时（绝大多数情况）这个式子退化成 `amount_minor × rate_ppm / 1_000_000`，与 2026-08-10 之前写的一致——**所以这不是改决定，是把一直漏掉的那一项补上**。跨 exponent 时漏掉它会差 10^|Δexp| 倍：AUD（2 位）→ JPY（0 位）少乘这一项，结果会大 100 倍。**中间量用 `i128`**，先乘后除。

### 4. 两个实体，一条时间轴，两个视图

**实体「交易」**：金额、币种、汇率、商户、分类、渠道、来源截图。

**实体「事项」**：同一条记录的**计划与结果**两端，状态为：

```
backlog（无计划）→ scheduled（有计划）→ done（明确完成）
          └──────────────→ archived（明确放弃，可恢复）
```

计划与结果属于同一实体，不拆成「待办」与另一张记录表。v1 的难逆数据形状是：

- 计划与结果分层；结果只保存用户明确提供或确认的变化，显示时未提供字段可回退计划，但不得把计划值复制成结果事实；
- 时间可以是单日不定时、时间点、最长 24 小时且可跨一次午夜的时间块，或不展开成每日记录的粗粒度日期范围；
- 截止日期/时间与计划正交，只有截止的事项仍是 backlog；
- 结果时间只在 done 生效，且可以为空；点击完成的系统时刻只进入审计；
- 过期不自动改期或退回，状态纠正由用户显式触发；
- 每个事项 v1 最多一组计划和一组结果，不支持多个不连续精确时间片段。

具体字段组合、自然语言 update 草稿与周视图行为由 [05 事项](../prd/05-items.md) 规定；[00 地基](../prd/00-foundation.md) 在 M3 落具体表结构。

**时间轴是共同骨架，但 UI 分两个视图**——不在同一张日历里混着显示钱和事项。

### 5. 草稿区与审计的结构约束

- `draft_*` 表与事实表**结构分离**，草稿表的 `source_id` 与原文片段字段**非空**。
- `audit_log` **append-only**：代码中不存在针对它的 `UPDATE` / `DELETE`。
- 所有可同步实体的 ID 用 UUID（不用自增整数），为将来的导出/合并留出空间——即使 v1 明确不做同步。

## 理由

**为什么 SQLite 而不是文件化存储（Markdown / JSON）**：审核界面要对几百到几千条记录做排序、过滤、按商户聚合、跨图去重；回顾要做时间维度聚合。这些是关系查询，文件化存储要么自己实现索引，要么每次全量扫。SQLite 直接给。**代价是数据不能用文本编辑器直接看**——用「纯文本导出」补偿。

**为什么禁止浮点**：`0.1 + 0.2 != 0.3` 在账本里意味着对账永远差一分钱，而 [ADR-0002](./0002-ai-never-writes-directly.md) 闸门 3 的总额交叉校验**恰恰依赖精确相等**。浮点会让唯一的自动纠错机制失效。这是「禁止」而非「不推荐」的原因。

**为什么三元组而不是「存原币 + 一张汇率表」**：汇率表方案要求「查询时按交易日期去查历史汇率」，而历史汇率在「数据不出本机」的前提下没有可靠来源（登记为 [`docs/PRD.md` §13](../PRD.md) 开放问题 P1）。三元组把折算结果冻结在交易发生的那一刻，事后汇率表变了也不影响已入账的历史。

**为什么计划与结果属于同一个事项，而不是两套业务实体**：见上文 §4。用户说「下周一 15:00 看牙」是在计划同一件事，后来补「15:15 才开始，看了 90 分钟」是在修正它的结果；拆成两条无关联记录会让目标匹配、回溯修改与审计失去锚点。**同一实体不等于混写字段**——计划与结果仍须分层，结果不得由计划自动填充。

**为什么 ID 用 UUID 而 v1 又不做同步**：改 ID 类型是全表迁移，成本远高于一开始就用 UUID。

## 后果

**得到**：

- 总额交叉校验可以做精确相等判断
- 证据链完整——任何一笔都能回到「截图上原本写的数字」
- 事项的计划与结果同锚点、分层保存；既能提前安排，也能事后回溯修正
- 用户能自己备份、能导出、能带走

**付出**：

- 所有涉及金额的代码都要显式处理「分」这个单位，写起来比 `f64` 啰嗦
- 三元组让交易表宽一些，且每次写入要保证三个值自洽（`本位币金额 == 原币金额 × 汇率`，在整数定点下带明确的舍入规则）
- 事项时间不再是单一 `scheduled_on / actual_minutes` 形状；M3 schema 与周视图必须表达时间粒度、稀疏结果覆盖、截止约束和显式状态修正
- 数据库文件不可读，调试要靠工具

**留给 sub-PRD 决定的**（本 ADR 不规定）：具体表结构、字段名、索引、迁移机制——那是 [`docs/prd/00-foundation.md`](../prd/00-foundation.md) 的范围。**本 ADR 只钉死不可逆的形状。**

**原「已知未决」已关闭（2026-08-07）**：本位币**可切换**（产品决定，[`docs/PRD.md` §13](../PRD.md) P2 关闭）。固定单一本位币等于在 schema 层重新引入地域假设，与 [`docs/PRD.md` §3.1](../PRD.md)「解析能力与国家/币种无关」矛盾。

切换语义由本 ADR §3 的「折算冻结在交易发生那一刻」直接推导，无需新增决策：**`base_currency` 逐笔存储、确认时冻结；切换只影响新交易，不改动历史行；跨切换点的汇总按本位币分组，不静默相加。** 完整规则与验收见 [`docs/prd/00-foundation.md` §3.4](../prd/00-foundation.md)。
