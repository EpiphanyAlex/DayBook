# 05 · 事项 Items

> v1 的「薄」模块。**做得薄是决定，不是妥协**——[`docs/PRD.md` §5](../PRD.md) 的范围纪律是「交易做深、事项做薄」。
> 依据：[ADR-0004 §4](../adr/0004-data-model-sqlite-integer-money.md)（两个实体、一条时间轴）与 [`docs/PRD.md` §5.2](../PRD.md)（事项是同一个实体的计划与结果两端）。

## 1. 问题

用户既需要提前安排，也需要事后回溯：

- 「下周一下午三点到四点看牙」是**计划**；
- 「3:15 才开始，看了 90 分钟」是用户事后提供的**结果**；
- 「周一到周三完成了客户方案」只说明事情发生在一个日期范围内，**没有说明每天都做、每天做了什么或每天用了多久**。

本模块此前从「时间没有像账单那样的客观痕迹」推出「不能记录实际时段，只能记时长」。这个推导过头了：**不能自动观测或编造，不等于不能记录用户明确陈述的事实。** 用户的口述或文字是来源原件，agent 可以把它整理成待确认的新建或修改草稿；用户确认后，计划与结果才能成为事项事实。

Daybook 也不是实时计时器。桌面应用的典型使用方式是低频、重型的集中整理：用户可以先计划，事情发生后再回来补充结果；不要求他在开始、暂停、结束的每一个时刻打开应用。

## 2. 范围与非目标

**范围**：事项实体与状态机 · 计划时间、结果时间、截止约束 · backlog · 单清单分组 · 自然语言批量新建与修改 · 周视图 · 拖拽/拉伸精调 · 完成、未完成与归档回顾 · 证据链与审计。

**非目标**（当前版本延期，不是永久禁止）：

- 提醒、通知
- 重复任务
- 子任务、任务依赖
- 优先级算法
- 番茄钟、计时器、`in_progress` 状态
- 日视图、月视图
- 系统日历同步、会议邀请、参与人、空闲时间计算、地点与视频会议等完整日历能力
- 多个不连续的精确计划/实际时间片段
- v1 不做每周实际用时汇总
- 弱信号采集自动生成事项（未来做，前置条件见 [ADR-0005 §4](../adr/0005-voice-and-system-integration.md)）
- **意图↔交易事实闭环**（待办「交房租 2000」被账单里的转账核销）——**v2**（[`docs/PRD.md` §11](../PRD.md)）

## 3. 决定与依据

### 3.1 一个事项：计划与结果两端

正式概念不再是「待办 + 时间日志」，而是**计划 + 结果**：

- **计划**回答「准备什么时候做」；
- **结果**回答「是否完成，以及用户明确补充的实际日期、时间或用时」；
- 两者属于同一条事项事实，不拆成两张互不相识的业务实体。

状态机：

```
backlog ──给出计划──▶ scheduled ──明确完成──▶ done
backlog / scheduled ──明确放弃──▶ archived

done ──用户明确纠正──▶ scheduled / backlog
archived ──用户明确恢复──▶ scheduled / backlog
```

`archived` 只表示放弃尚未完成的事项：允许 `backlog / scheduled → archived`，不允许 `done → archived`。若一条 done 记录其实没有完成，先经待确认纠正回 backlog/scheduled，再决定是否归档。

| 状态 | 含义 | 时间约束 |
|---|---|---|
| `backlog` | 已记下，但没有计划日期/时间/范围 | 可以有截止日期；**只有截止不等于已安排** |
| `scheduled` | 已有一组计划时间表达 | 计划可以是不定时日期、时间点、时间块或日期范围 |
| `done` | 用户明确确认已完成 | 结果时间可以完整、部分或全部为空 |
| `archived` | 用户明确放弃，默认从活动视图隐藏 | 可经自然语言待确认变更恢复 |

状态规则：

- 过了计划日期仍未完成，**不自动移动、不自动改期、不自动退回 backlog**；原计划保留，并进入「待处理」区域。
- 用户明确纠正「其实还没完成」时，允许 `done → scheduled`（仍有计划）或 `done → backlog`（没有计划）。由于结果时间只对 done 生效，回退 patch **必须显式清空结果层**；before/after 在确认界面可见，旧结果只留在不可变草稿与审计历史中。
- 进入 `archived` 时旧计划保留但标为不生效，供归档详情与审计查看。恢复默认产生一条「清空旧计划 + 回到 `backlog`」的待确认 patch；用户同时给出新计划时，patch 明确以新计划替换旧计划并回到 `scheduled`。不得得到「backlog + 生效计划」的组合。v1 不提供常驻的手动恢复控件，恢复走自然语言待确认路径。
- `backlog → done` 合法：用户可以第一次提到一件事时就直接补记它已经完成。
- `marked_done_at` 只表示用户何时在 Daybook 里执行了确认/完成动作，属于审计事实；**它不是事情实际发生的时间**。

#### 交易与事项的边界：钱是否已经流动

判据仍是「钱是否已经流动」，不是「有没有金额」：

| 用户说的 | 归属 | 为什么 |
|---|---|---|
| 「今天吃饭 180」 | 交易 | 钱动了 |
| 「上周那 400 是给家里买茶叶」 | 交易 | 钱动了（补记旧账） |
| 「明天交房租 2000」 | 事项 | 钱还没动；`2000` 只进入标题/备注，不建结构化金额字段 |
| 「这周要去银行办卡」 | 事项 | 未发生、无金额 |
| 「昨天 3:15 看牙，看了 90 分钟」 | `done` 事项 | 用户在回溯一件已发生的事 |

实体判断错时走 [03 审核 §3.6](./03-review.md) 的一键改实体类型，不让 agent 直接写事实表。

### 3.2 时间表达：允许精确陈述，不允许自动编造

计划与结果各自最多有**一组**时间表达。v1 支持以下粒度：

| 粒度 | 示例 | 含义 |
|---|---|---|
| 无日期 | 「约牙医」 | 未安排 |
| 单日不定时 | 「周一交房租」 | 周一做，几点未说明；UI 称「不定时」，**不称「全天」** |
| 时间点 | 「周五 9:30 寄快递」 | 有开始时间、没有计划时长；不得擅自补成 30 分钟 |
| 时间块 | 「周五 16:00–17:00 看牙」 | 开始时间 + 时长；结束时间由两者计算，不独立存储 |
| 日期范围 | 「周一到周三完成客户方案」 | 过程落在周一至周三之间；**不展开成三天记录，不推断每天都做或每日用时** |

共同规则：

- 日期与分钟使用用户当时理解的**浮动本地民用时间**；切换系统时区后不做换算。
- 数据精度为 1 分钟；周视图拖拽默认按 15 分钟吸附。
- 单个时间块的时长为 1–1440 分钟，可跨越一次午夜；周视图按日期边界切片显示，但两段仍指向同一事项。
- 连续多天但没有具体时段的信息使用日期范围；v1 不支持任意多个不连续的精确时间片段。
- 结果时间只在 `done` 状态生效。点击「完成」不会自动生成实际日期、开始时间或用时。
- 一个此前未记录的完成事项若没有说日期，待确认草稿以来源提交日作为结果日期；匹配到已有计划事项且用户没有纠正日期时，沿用计划日期。两种默认都必须在确认界面可见。

#### 计划与结果按字段覆盖

用户只改他说到的字段：

- 「看了 90 分钟」只覆盖用时，开始时间继续沿用计划值显示；
- 「3:15 才开始」只覆盖开始时间，未提到的计划时长继续显示；
- 「周一到周三完成」把结果粒度改为日期范围，不生成每日片段；**日期范围一旦明确，就整体覆盖计划中的具体开始时间与时长，不得拼成「周一到周三每天 15:00」**。

未报告的计划值**不复制**进结果字段；结果层必须保留「未提供 / 明确清空 / 提供新值」三种 patch 语义。有效显示解析器逐字段遵守：

- `set(value)` → 显示新值；
- `clear` → 显示为空，**并抑制计划回退**；
- `unspecified` → 回退显示计划值。

结果日期范围一旦 `set`，同时抑制计划中的具体开始时间与时长。结果存在时，主视图只显示解析后的结果；原计划保留在事实数据与 append-only 审计日志中，不在周视图重复画一份。

### 3.3 截止约束独立于计划

`due_on`（截止日期）与可选的截止分钟回答「最晚什么时候完成」，不回答「准备什么时候做」。

- 只有截止日期/时间的事项仍是 `backlog`。
- 「周一到周三做客户方案」是计划日期范围；「周三前交客户方案」是截止约束；两者可以同时存在。
- 截止时间同样是浮动本地时间，精度到分钟。
- 截止约束不生成提醒、不自动安排、不占用小时格。
- 周视图在独立「截止」轨道展示；同时有计划的事项还可在自身卡片显示截止标签。

### 3.4 自然语言新建与修改都先进入草稿

事项草稿不只表示「新建」，还必须表示「修改已有事项」：

- `operation = create`：起草一个新事项；
- `operation = update`：带仅包含用户明确修改字段的 tri-state patch，并有 `resolution_state = ready | needs_target`；
- `ready` update 必须有 `target_item_id`；`needs_target` update 的目标为空，并冻结 0–8 个候选 id。两种都是真实 `draft_items` 行、都计入 `complete_source.item_count`，但 `needs_target` 不可确认；
- `drafted_json` 不可变，必须包含 operation、resolution_state、目标/候选与原始 patch；
- 每条草稿都带 `source_id`、`attempt_id`、`source_ordinal` 与 `evidence_text`，与交易草稿共用 [ADR-0002](../adr/0002-ai-never-writes-directly.md) 的证据链；
- agent 找不到唯一目标时 fail closed：界面要求用户选择候选、改为新建或忽略，**不得静默新建重复事项**。人的选择把草稿改成 confirmable 状态并写审计，`drafted_json` 仍保持 agent 原始输出；
- 一段口述可以混合多个新建与更新草稿，整段原文、全部差异与条数并排后一次批量确认；
- 只有确认动作能写 `items` 事实表。agent 工具仍只能写 `draft_items`。

#### 有界候选契约

应用不把 `items` 全表交给 agent。M3 提供只读 `find_item_candidates` 工具：

- 入参是 agent 从当前来源提取的目标描述与可选时间提示；
- 确定性代码只返回最多 8 个候选的 `id / title / status / plan摘要 / result摘要 / due / list`，不返回原始来源、审计或全部备注；
- `draft_item` 只接受本次候选查询返回的 target/candidate id，拒绝 agent 自造或越界 id；
- 找到唯一目标时写 `ready` update；零个或多个仍无法唯一确定时写 `needs_target` update，并把候选快照保存在草稿中；
- 用户选择候选后无需再次调用 agent；domain 将草稿目标设为所选 id、转为 `ready`，并写人工审计。用户选择「改为新建」时同样由 domain 改 operation，保留原始 `drafted_json`。

示例：

> 牙医 3:15 才开始，看了 90 分钟；客户方案是周一到周三完成的；房租改到周五处理。

应得到三条待确认变更，分别更新实际时间、实际日期范围与计划日期；不能把它们合并成一条自由文本，也不能由 agent 直接改事实。

#### 人的确定性操作不绕草稿兜圈

用户在周视图中直接拖拽或拉伸，是确定性的人工操作：

- 未完成事项的拖拽/拉伸修改计划；
- 已完成事项的拖拽/拉伸修改或创建结果时间；
- 操作立即生效、显示「撤销」，并写 `actor = human` 的审计；
- 撤销再写一条反向审计，不删除历史；
- 自然语言修改仍必须走草稿确认，因为其中存在 agent 的目标匹配与语义解释。

多字段表单不进入主路径；只作为 agent 不可用、精确修复或无障碍操作的隐藏兜底。拖拽也不得成为唯一入口，所有操作必须有键盘可达的等价路径。

### 3.5 单清单分组，不做标签系统

每个事项最多属于一个用户自定义清单：

- 清单有名称和颜色；
- 未选择时为「未分组」；
- 清单用于周视图着色、筛选与浏览；
- 不支持多标签、层级清单或优先级算法。

颜色不得成为唯一状态信号。清单与事项时间是正交维度，改清单不改变计划或结果。

#### 默认清单只种入一次（**M3**，2026-08-24 产品决定）

首次建账时种入 5 个默认清单，**命名统一两个汉字**，与 [04 §3.3](./04-transactions.md) 的默认分类同一条文案约定：

| 顺序 | 名称 | 覆盖 | 颜色 |
|---:|---|---|---|
| 1 | 工作 | 本职工作与职业相关的事 | `{colors.chart-1}` |
| 2 | 家务 | 家里要做的事、维修、采买安排 | `{colors.chart-2}` |
| 3 | 健康 | 就医、复查、运动安排 | `{colors.chart-3}` |
| 4 | 学习 | 课程、考试、要读的东西 | `{colors.chart-4}` |
| 5 | 钱事 | 缴费、报税、对账这类与钱有关的待办 | `{colors.chart-5}` |

- 种入后与用户自建清单**同权**，应用升级不把用户删除或改名的默认清单补回来（与 [04 §3.3](./04-transactions.md) 一致）
- 颜色取 [`design.md`](../../design.md) 的分类色序前五档，**不另立调色板**；`{colors.chart-1}`–`{colors.chart-4}` 是第一环，`{colors.chart-5}` 起是第二环，同环内亮度一致，灰度打印仍能靠 hue 区分
- **清单与 [04 §3.3](./04-transactions.md) 的账目分类是两套东西**，不共享实体、不互相映射：「钱事」是一件要做的事（去缴费），「保险」是一笔已经花掉的钱。名字相近的地方尤其不要合并

### 3.6 周视图：呈现，不替用户决策

v1 只有周视图。**一周从哪天开始由设置决定，默认周一**（**M3**，2026-08-24 产品决定）——它同时决定周视图的七列边界与本节末「这周完成了什么」的归属窗口，两处必须读同一个设置，不得各自写死。改这个设置**不改动任何事项数据**，只改分组呈现。

由上到下包含：

1. **截止轨道**：截止日期/时间标签，不占用时间格；
2. **跨日事项轨道**：计划或结果的日期范围；
3. **不定时轨道**：有日期但无开始时间的事项；
4. **小时时间格**：时间点与时间块；
5. **未安排区域**：没有计划的事项，含只有截止约束的事项；
6. **待处理区域**：已逾期、即将截止或需要重新安排的事项。

交互与显示：

- 时间块重叠时允许保存并并排显示；只提示「与另一事项重叠」，不自动改期、不判断优先级。
- 日期范围是一条横跨起止日期的粗粒度条带，**不表示每天全天被占用**。
- 已完成事项默认继续显示，支持「隐藏已完成」筛选；没有计划也没有结果日期的完成事项只进「完成时间未知」列表，**不得用 `marked_done_at` 把它归进某一周**。
- 完成事项有结果时显示结果；结果字段缺失时按 §3.2 的 set/clear/unspecified 解析器处理。原计划不另画虚线副本。
- 拖动跨午夜时间块的任一切片修改同一事项；不得产生两个事项。
- 拖动日期范围移动整个范围，拉伸两端改变起止日期；均按 §3.4 立即生效并可撤销。

#### 「待处理」与周回顾的确定性归属

全部比较使用当前浮动本地时间：

- 单日不定时和日期范围在最后一天结束时过期；时间点在该分钟过去后过期；时间块在导出的结束分钟过去后过期。
- `scheduled` 且计划结束早于当前时刻 ⇒ 「需要重新安排」。系统只列出，不自动移动。
- 未完成且截止边界早于当前时刻 ⇒ 「已逾期」；只有截止日期时，边界是当天结束。
- 未完成且截止边界处于当前时刻至未来 7 个自然日内 ⇒ 「即将截止」。这是 UI 分组窗口，不产生通知。
- 「这周完成了什么」只纳入有效结果时间与当前可见周相交的 done 事项；没有结果日期时按 §3.2 回退计划日期/范围。计划与结果日期都没有的 done 事项进入「完成时间未知」，不归属任何周。

### 3.7 回顾回答状态问题，不制造时间报表

v1 的事项回顾回答：

1. 这周完成了什么；
2. 什么没做完；
3. 什么需要重新安排；
4. 什么即将截止或已经逾期。

单条事项可以保存用户明确报告的实际用时，但**不做每周实际用时汇总**。缺失就是缺失，不用计划时长填补结果，也不以不完整数据制造精确报表。

## 4. 否决的替代方案

| 方案 | 否决原因 |
|---|---|
| 因为没有自动痕迹，就禁止记录实际开始时间 | 用户明确口述本身就是来源；应禁止的是自动编造，不是禁止用户回溯 |
| 把计划时间复制成结果时间 | 会把意图静默伪装成事实；结果字段只存用户明确报告或确认的默认值 |
| 点击完成时记录点击时刻为实际完成时刻 | 用户可能晚上才补记白天发生的事；记录动作时间与事情发生时间不是一件事 |
| 增加 `in_progress` 与计时器 | 违背桌面端低频集中整理的使用方式，并扩张成实时追踪工具 |
| 过期后自动改期或退回 backlog | 替用户决策，还会抹掉「原本计划但没做成」的信息 |
| 冲突时自动寻找空档 | 属于优先级/日程优化算法；视图只负责把冲突呈现给用户 |
| 把日期范围展开成每天一条 | 用户没有说每天都做；展开会制造不存在的事实 |
| 用多个事项表示跨午夜时间块 | 同一件事被错误拆成两件；数据层可由开始时间 + 时长自然表达 |
| v1 支持任意多个不连续精确时间片段 | 编辑、拖拽与审核复杂度显著上升；先用单组时间表达和粗粒度日期范围验证 |
| 把自然语言修改直接写入事实表 | 目标匹配和字段解释都可能错，违反 [ADR-0002](../adr/0002-ai-never-writes-directly.md) |
| 把多字段表单作为主路径 | 重新引入产品要消除的逐条表单摩擦 |
| 把 Daybook 做成完整日历 | 当前范围只管理事项的计划与结果；提醒、同步、会议等能力延期 |

**人工验收**：

1. 输入「下周一 3 点到 4 点看牙，周五 5 点前交方案」→ 一次确认后，牙医进入时间格，方案截止进入截止轨道但仍未安排。
2. 事后输入「牙医 3:15 才开始，看了 90 分钟；方案是周一到周三完成的」→ 两条 update 草稿显示字段差异与原文，确认后牙医显示 15:15–16:45，方案显示为跨日完成范围；没有每日片段被编造。
3. 将已完成牙医拖到 15:30 并拉长到 105 分钟 → 修改结果而非计划，提示可撤销；撤销后两条审计都存在。
4. 创建两个重叠时间块 → 两者并排可见，系统不自动移动任一条；全流程可不用鼠标完成。
