# 04 · 交易 Transactions

> v1 的「深」模块。目标是**能真正替代手工流程**——不是「也能记账」，是「不再打开原来的记账软件」。
> 依据：[ADR-0004 数据模型](../adr/0004-data-model-sqlite-integer-money.md)、[`docs/PRD.md` §5.1](../PRD.md)。

## 1. 问题

一笔交易要能同时回答五件事：付了多少（原币）、折合多少（本位币）、当时什么汇率、走的哪个渠道、这钱花在什么上。**任何一项缺失，回顾时就要重新翻截图**——而那正是产品要消灭的动作。

**其中多币种最容易被做错。** 多数记账工具只存换算后的结果，于是原始金额丢失、汇率不可考、事后无法与账单核对。

而多币种对本产品**不是边缘情况**：解析能力天然不区分币种（[`docs/PRD.md` §3.1](../PRD.md)——它不认识具体格式，也就无从被币种局限），用户账户里出现几种货币只取决于他自己的生活，产品不该因此掉一档。**渠道同理**：不预设任何国家的银行或支付平台清单，渠道集合由用户自己维护。

## 2. 范围与非目标

**范围**：交易实体的字段语义 · 多币种三元组的读写规则 · 商户与分类 · 渠道 · 手工新建/编辑/删除 · 基础回顾。

**非目标**：

- **草稿的产生与确认流程**——属 [02 导入](./02-ingest.md) 与 [03 审核与草稿区](./03-review.md)
- **商户→分类映射的学习**——属 [06 记忆](./06-memory.md)；本模块只**消费**规则
- **预算、账户余额推演、投资持仓**——v1 不做
- **意图↔事实闭环**（待办「交房租 2000」被账单里的 2000 转账核销）——**v2 的奖励，不是 v1 的门票**（[`docs/PRD.md` §11](../PRD.md)）
- **在线汇率查询**——违反「数据不出本机」（[ADR-0001](../adr/0001-local-first-desktop-platform.md)）

## 3. 决定与依据

### 3.1 交易的字段语义

| 字段 | 说明 |
|---|---|
| `occurred_on` | 交易发生的**本地日历日**（`YYYY-MM-DD`，不带时区）——用户说「8 月 3 号那笔」指的是这个 |
| `amount_minor` + `currency` | **原币三元组之一**：用户实际付出的数字，与截图上完全一致 |
| `base_amount_minor` | 折算到本位币的金额 |
| `base_currency` | **本次折算所用的本位币**——逐笔存储、确认时冻结。本位币可切换，切换只影响新交易（[00 地基 §3.4](./00-foundation.md)「本位币切换语义」） |
| `rate_ppm` | 折算所用汇率 × 1_000_000 |
| `direction` | `expense` / `income` / `transfer` |
| `merchant` | 商户原文（**保留 agent 从截图读到的原始文本**，不做归一化覆盖） |
| `merchant_normalized` | 归一化后的商户名，由记忆规则产生，可空 |
| `category` | 分类 |
| `channel` | **支付方式类别**，形如 `bank_debit` / `bank_credit` / `wallet` / `cash`。取值集合**由用户自己维护**（§3.4），产品不预设任何国家的银行或支付平台清单 |
| `account_id` | **具体账户 / 卡**（§3.4）。**列与 `accounts` 骨架表 M0 就建**，业务在 M2；M0/M1 恒为空 |
| `source_id` | 来源（证据链锚点） |
| `note` | 用户备注 |
| `confirmed_at` | 人工确认时间（非空——事实表的记录必然经人确认） |

**`merchant` 与 `merchant_normalized` 分开存**：归一化是可变的（记忆规则会演进），原文是证据的一部分，不能被覆盖。

### 3.2 三元组的读写规则

依据 [ADR-0004 §3](../adr/0004-data-model-sqlite-integer-money.md)、[00 地基 §3.4](./00-foundation.md)。

- **全部非空**，写入时校验自洽。**公式带币种 exponent**（2026-08-10 改，[00 地基 §3.4](./00-foundation.md)「换算公式」）：

  ```
  base_amount_minor == round_half_even(
      amount_minor × rate_ppm × 10^exp(base_currency)
      ÷ (1_000_000 × 10^exp(currency))
  )
  ```

  本文 v0.1–v0.5 写的是 `amount_minor × rate_ppm / 1_000_000`——**那只在两边都是两位小数时正确**。JPY（exp 0）/ KWD（exp 3）参与换算会差 10^|Δexp| 倍
- `rate_ppm` 是「1 **主**单位原币 = 多少 **主**单位本位币」× 1_000_000——**就是账单上印的、用户会手填的那个数**
- **原币与本位币相同时走同一套**，`rate_ppm = 1_000_000` 且两边 exponent 必然相等，**不设特例分支**
- **`base_currency` 逐笔冻结**：本位币可切换，但切换只影响新交易，已确认的行永不改动（[00 地基 §3.4](./00-foundation.md)）
- **不得只存换算后的结果**——证据链会断（回不到「截图上写的到底是多少」）
- **不得在录入时要求用户手算**——汇率折算是产品的活

**汇率从哪来**（v1 的三条路径，按优先级）：

1. **截图自己给的**——很多信用卡账单同时印了原币金额与折算后金额，agent 两个都读，汇率反推得出
2. **用户手工填**——审核界面可编辑
3. **沿用同日同币种对已有交易的汇率**——同一天的多笔用同一个汇率

**没有第四条路径**：v1 不查在线汇率 API（登记为 [`docs/PRD.md` §13](../PRD.md) 开放问题 P1）。三条都不可用时，该条草稿标为「缺汇率」，**不入库**。

### 3.3 分类

- **一层分类，不做多级树**——v1 的用户是一个人，多级树是给会计事务所用的
- 内置一组默认分类，用户可增删改
- 分类的**自动建议**来自 [06 记忆](./06-memory.md) 的商户→分类映射；**建议不等于决定**，用户在审核界面可改

### 3.4 账户与渠道是两个维度（2026-08-10 改，产品决定）

| 维度 | 是什么 | 例 | 何时启用 |
|---|---|---|---|
| `channel` | **支付方式类别** | `bank_debit` / `bank_credit` / `wallet` / `cash` | v1 全程 |
| `account_id` | **具体账户或卡** | 「主力储蓄卡」「那张里程信用卡」 | **业务在 M2**；列与 `accounts` 骨架表**在 M0 就建**（[00 地基 §3.6](./00-foundation.md)） |

**此前只有 `channel` 一个维度，而它的取值示例是支付方式类别——于是「我这笔刷的是哪张卡」在结构上无法表达。** 这与 [`docs/PRD.md` §2](../PRD.md) 直接冲突：那里说痛感随「**账户数** → 支付渠道数 → 币种数」递增、多账户用户是首要验证场景。**产品把多账户当作核心痛点，数据模型里却没有账户。**

后果不止是回顾少一个维度：

- [02 导入 §3.6](./02-ingest.md) 的**跨图去重**——同一笔在信用卡账单与银行流水各出现一次是典型重复，而两笔真的刷了同样金额的消费**分属不同账户**是典型非重复。没有账户维度，这两种情况在数据上长得一样
- 本文 §5 **R3 转账双边**——「从 A 账户转到 B 账户」这句话里的 A 和 B 无处可存

三条规则：

- **两者正交**，不是一个维度的粗细两档：同一个账户可以有多种支付方式（一张卡既能刷信用也能取现），同一种支付方式跨多个账户
- **渠道与币种也是两个维度**——同一张卡可能有多币种账户（本条自 v0.1 起未变）
- 两者的取值集合**都由用户自己维护**（增删改），**不预设任何国家的银行或支付平台清单**——预设清单等于把产品绑定到特定地域

**M0/M1 明确不做业务**：`accounts` 的字段补全、写入路径与 UI 都在 M2，M0/M1 期间 `account_id` 恒为空。

**但表本身在 M0 就要建骨架**（2026-08-10 修正，此前本行写「表与 UI 都在 M2」）：SQLite 的外键在**父表不存在**时，`PRAGMA foreign_keys = ON` 下**连插入 `NULL` 都会报 `no such table: main.accounts`**（[00 地基 §3.6](./00-foundation.md) 有实测记录）。「留列不留表」这个组合**跑不起来**——M0 的第一条 `INSERT INTO transactions` 就会挂。

留列（+ 骨架表）的理由不变：成本是四列和一条迁移语句，不留的成本是把回顾、去重、导出在 M2 改两遍。**骨架表别提前加字段**——机构、币种、卡号后四位、初始余额这些要等 M2 拿到真实账单再定。

### 3.5 手工录入

**手工填表是兜底，不是主路径**（2026-08-08 改定）。

`docs/PRD.md` §1.1 把录入摩擦确认为痛点的另一半，而我们的解法是**不用表单**——「今天现金吃饭 180」说一句话比填五个字段快得多，走 `kind = utterance` 来源（[02 导入 §3.1](./02-ingest.md)）。因此：

- **主路径**：说话 / 拖图 → agent 起草 → 审核确认
- **手工表单只在两种情况下用**：① agent CLI 不可用（`probe()` 失败，见 [01 Agent 运行时 §3.5](./01-agent-runtime.md)）② 用户要**改一条已入库的旧交易**
- **UI 不给它显眼的「+ 新建」按钮**。它是降级路径，不该和主路径平级呈现

保留它而不是删掉的理由：`01 §3.5` 已经要求「后端不可用时应用仍可启动」。如果那时连记一笔都做不到，应用就是块砖头。

字段与约束：

- 手工新建的交易 `source_id` 为空——**这是唯一允许无来源的路径**，且必须由人触发
- agent **没有**创建无来源交易的能力（工具面里不存在，见 [01 Agent 运行时 §3.2](./01-agent-runtime.md)）
- 编辑与删除都写 `audit_log`；删除是软删除（保留审计可回溯性）

### 3.6 基础回顾

v1 只回答少数几个问题，**不做通用 BI**：

- 这段时间总支出（按本位币）
- 按分类的分布
- 按渠道的分布
- 按币种的分布（多币种用户的特有需求）
- 时间序列：按天/周的支出曲线

**回顾一律以本位币汇总**，但明细行同时显示原币——这是多币种场景的核心体验。

**若查询区间跨越了本位币切换点**，汇总按 `base_currency` **分组呈现，不静默相加**——把两种本位币的金额加在一起会得到一个无意义的数字（[00 地基 §3.4](./00-foundation.md)「本位币切换语义」规则 3）。UI 在这种情况下显式标注「此区间含两种本位币」。

## 4. 否决的替代方案

| 方案 | 否决原因 |
|---|---|
| 只存本位币金额 | 证据链断裂：回不到「截图上写的到底是多少」（[ADR-0004](../adr/0004-data-model-sqlite-integer-money.md) §3） |
| 存原币 + 一张历史汇率表，查询时折算 | 历史汇率在「数据不出本机」下没有可靠来源（[`docs/PRD.md` §13](../PRD.md) P1）；三元组把折算冻结在交易发生那一刻，事后汇率表变了不影响历史 |
| 调在线汇率 API 补全汇率 | 直接违反 [ADR-0001](../adr/0001-local-first-desktop-platform.md)「数据不出本机」——请求本身会泄露用户的交易日期与币种对 |
| 多级分类树 | v1 单用户场景下是纯复杂度；扁平分类 + 记忆规则已能覆盖 |
| 归一化后覆盖 `merchant` 原文 | 原文是证据的一部分；归一化规则会演进，覆盖后无法重算 |
| 硬删除交易 | 破坏审计可回溯性（[ADR-0002](../adr/0002-ai-never-writes-directly.md) 闸门 4） |
| v1 就做预算与账户余额推演 | [`docs/PRD.md` §6](../PRD.md) 非目标；余额推演要求交易集合完整，而回溯记录天然不完整 |
