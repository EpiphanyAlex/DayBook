# docs/prd 写作纪律

> Claude Code 在读写本目录下任何文件时会自动加载本文。它的唯一目的：消灭**「指称对象活在作者脑子里，没落在纸面上」**这类缺陷。
> 本目录文档的读者是**没读过你对话的人**和**无记忆的 agent**——任何依赖会话上下文才能看懂的句子，都是缺陷。

## 硬规则（写作时）

1. **指称自包含**：凡写「两份文档 / 另一个模块 / 该方案 / 上述做法」，必须**点名并链接全部对象**。反例：「现两份文档互相矛盾」却只点名一份；正例：「它与 [architecture §3](../architecture.md) 对同一条写入路径的顺序互相矛盾」。
2. **编号首现展开**：模块号、里程碑号、决策号在一份文档中首次出现时必须带名字——写「03 审核与草稿区」「M2 批量与多币种」「开放问题 P1（历史汇率数据从哪来）」，不写裸「03」「M2」「P1」。
3. **路径真实**：引用的文件/目录必须存在；规划中尚未创建的，同一行标注「待建」。
4. **frontmatter 必填**：本目录全部 `.md`（sub-PRD 与索引类）——`title` · `status` · `owner` · `date` · `version`。
   **本项目不用 ticket，因此没有第二套 frontmatter 字段**（依据 [`CLAUDE.md`](../../CLAUDE.md)「PRD 体系与工作流」）。
5. **跨文档一致性**：改动一个共享决定（schema、契约、状态语义、错误码）时，grep 本目录**所有**提及处同步——两处各说各话比没写更糟。
6. **结论带出处**：来自会话、PR 评论、口头讨论的结论落进文档时，必须附来源链接（ADR / 文档 / 章节），不许凭空出现。

## 两条结构性原则

**零沉默原则**
任何两份 sub-PRD / 两次实施必须达成一致的东西（schema、契约、约定、状态语义），在文档里要么**被决定**（标依据），要么**显式挂起**（标谁来决、何时决）。**唯一不允许的状态是沉默**——沉默会被每次实施用自己的假设填掉，且各填各的。

**深度花在边界上，不花在内部**
sub-PRD 只规格化**模块边界**（接口、schema、状态语义、错误码）。内部实现自由度（函数组织、内部命名、文件怎么分）**不规格化**——那是 agent planning 的空间。把边界写死、把内部放开，才能既不撞车又不越权。

## sub-PRD 的结构

```yaml
---
title:
status: draft | ready | in-progress | review | done | blocked | archived
owner: "@alex"
date: 2026-08-06
version: v0.1
---

## 1. 问题            这个模块解决什么
## 2. 范围与非目标
## 3. 决定与依据      架构选择，每条标依据（零沉默原则）
## 4. 否决的替代方案  为什么不那样做
## 5. 待决与风险      标谁来决、何时决
## 6. 验收标准        ⭐ 尽量写成可执行的命令，不是散文
## 7. 回流记录        实现证伪规格时回写这里
## 变更记录
```

**没有「工作拆分」一节。** 把 sub-PRD 拆成执行单元是 **agent 在 plan 阶段该做的事**，人预先拆完等于替 agent 做了它更擅长的工作。

### status 生命周期

```
draft → ready          规格写完、可以开工
ready → in-progress    开始实现
in-progress → review   验收标准全部跑过
review → done          回流写完、INDEX.md 已同步
任意 → blocked         发现阻塞依赖（必须在「待决与风险」写明是什么）
任意 → archived        该能力被砍或被并入别处
```

改 `status` 时**必须同步 [INDEX.md](./INDEX.md)**——两处不一致即缺陷。

## 验收标准要写成「给 agent 跑」，不是「给人勾」

这是本项目相对传统 ticket 体系最有价值的一处升级，**务必落实**：

```markdown
❌ 给人勾（传统 ticket 写法）
- [ ] 幂等：并发双导入同一张截图只产生一条 source 记录

✅ 给 agent 跑
- [ ] `cargo test ingest::idempotent_source` 通过
- [ ] `node scripts/verify-m0.mjs`（待建）退出码 0
```

理由和整个产品的哲学同源：**把「你信不信 agent 说完成了」换成「跑一下就知道」**——正如产品里把「信任 AI 的解析」换成「扫一眼原文 + 总额对账」（[ADR-0002](../adr/0002-ai-never-writes-directly.md)）。

**写不成命令的（如「UI 手感」「40 笔 30 秒审完」），标注为人工验收并写清操作步骤与判定阈值**，不要含糊成一句形容词。

## 回流义务

**计划易失，决定回流。**

agent 的实施计划是一次性的，不进 git。但 planning 或实现过程中**证伪了规格**（例：「sub-PRD 里的 schema 行不通，因为 X」），必须：

1. **先改 sub-PRD，再写代码**
2. 在「7. 回流记录」留一行：改了什么、为什么、依据哪次实现
3. 版本号 **+0.1**，并在「变更记录」加一行

**这是防文档腐烂的唯一机制。`docs/prd/` 落后于实现即缺陷。**

## 交付自检（完成任何 docs/prd 写作后必做）

1. 跑机械检查（frontmatter 完整性 + 相对链接可达）：

   ```bash
   node docs/prd/check-docs.mjs
   ```

   - **做什么**：扫本目录全部 `.md`——① frontmatter 缺必填字段（见硬规则 4）报错；② `[文字](相对路径)` 链接的目标文件不存在报错（同行标「待建」豁免；http 外链与纯 `#锚点` 不查）。
   - **何时跑**：改完 `docs/prd/` 任何文件、commit 之前；没改文档不用跑。
   - **红了怎么办**：按输出的「文件:行号:问题」逐条修，重跑到绿（`✓`）再交付；**禁止带红提交**。

   （脚本 CI-ready，靠退出码报成败；接入 CI 使其对所有 PR 物理强制，待 `.github/workflows/`（待建）建立后进行——当前为交付前手动门禁。）

2. 人工过一遍**悬空指称**（机器查不了语义）：文中每个「这 / 该 / 两份 / 另一个 / 上述」，指称对象是否已在**本句或本行**点名？每个从对话里搬来的结论，是否带了出处？

3. 若本次写作改动了 `status`，确认 [INDEX.md](./INDEX.md) 已同步。
