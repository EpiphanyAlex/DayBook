# Daybook 总 PRD

> Daybook（日簿）是一个跑在本地的 AI 桌面助手，帮用户把过去一段时间的钱和事补记回来。
> 本文定义**做什么、做到什么算成功、明确不做什么**，以及里程碑与各 sub-PRD 的对应关系。**范围变更必须先改本文。**
> 技术选择的完整论证在 [`docs/adr/`](./adr/)；术语定义在 [`docs/CONTEXT.md`](./CONTEXT.md)；系统结构在 [`docs/architecture.md`](./architecture.md)。

---

## 1. 问题

记账工具的设计前提是「交易发生时你会记一笔」。

**这个前提在实际使用中几乎不成立。** 人在付款当下不会掏出 app 记账——排队、赶路、和人说着话。于是记录被推迟，推迟到某个时刻用户坐下来，面对一堆已经模糊的痕迹，试图把过去一两周重建出来。

**现有工具在这一步把用户丢掉了。** 它们为「当场记录」持续优化——快捷输入、桌面小组件、快捷指令、语音速记——却把「事后重建」原样留给用户手工完成：翻银行流水、对截图、逐条敲进去、算汇率、查这笔到底是什么。**补记一次的成本远高于当场记十次**，于是用户放弃，工具沦为装了没用的那一个。

Daybook 的设计前提相反：**默认你是事后补的。** 产品的全部工作是把「重建过去」这件事的成本压到可接受。

由此确定两件事：

- **AI 的角色是考古学家，不是输入框。** 从截图等痕迹里把过去还原出来，摆到用户面前，用户只负责审。核心动作是**重建**，不是**录入**。
- **产品是低频、重型的**——一两周一次坐下来处理完，不是日常高频工具。

## 2. 用户

**主用户：想记账、但坚持不下来的人。**

放弃的原因通常不是不想记，而是补记的成本太高。这不是一个小众人群——它是记账工具共同的流失点。

**不需要用户具备任何特殊属性。** 「当场记不了、只能事后补」不是用户细分，是使用常态；把它当细分来定位会把问题写小。

**痛感强度随三个维度递增**：账户数 → 支付渠道数 → 币种数。这三项越多，手工整理越不可行，产品的价值越明显。因此多账户 / 多渠道 / 多币种用户是**最先被救到的人群**，也是本项目的 dogfooding 验证场景（作者本人：澳洲银行卡 + 信用卡 + 微信 + 支付宝，AUD/CNY 双币种）。

**但这是压力测试场景，不是市场边界。** 产品不依赖任何特定国家、银行或币种——理由见 §3.1：解析能力不认识具体格式，因此天然与地域无关。

v1 不服务：多人协作、家庭共享账本、企业报销。

## 3. 产品原理

三条互相支撑的判断，解释「为什么这个产品现在才可能，以及为什么只能长成这个形状」。

### 3.1 用户自带 AI 额度 → 边际成本为零 → 可以对任意来源做重解析

传统记账 app 必须为每家银行、每个支付平台写**专用解析器**。这条路线有三个固有缺陷：格式改版就挂、长尾永远覆盖不到、**每进入一个新国家都要重做一遍**。按 API 计费的竞品即使用了模型，算完 token 账也会退回去写解析器。

自带额度让「对着任意截图直接说读吧」成为可能。**这条能力天然与银行、币种、国家无关——因为它根本不认识具体格式**，也就无从被格式局限。多币种、多渠道、任意版式都是这一条的自然结果，不需要为它们单独设计。

### 3.2 用户已安装的 agent CLI 就是成熟的 agent runtime

Claude Code、Codex 本身已具备多轮推理、工具调用、上下文管理。产品需要的是「下达任务、它自己编排」，而不是「一个能调 API 的输入框」。

这也是**必须做成桌面应用**的理由：要调用本机登录态、本机进程、本机文件（[ADR-0003](./adr/0003-agent-runtime-and-pluggable-backend.md)）。

### 3.3 本地优先，无账号、无后端

账目与日程极私密。数据不出本机 → 隐私天然成立、无各国合规问题、零服务器成本。这也是一个人能长期维护的唯一形态（[ADR-0001](./adr/0001-local-first-desktop-platform.md)）。

## 4. 数据可信性：AI 永不直接写入账本

视觉模型会把 168 读成 1680。账本与普通 AI 应用的差别在于错误的性质：**账本错一个数字，用户信任就永久归零，且不可逆**——一旦用户开始回头核对原始截图，产品声称节省的时间就全部吐了回去。

四道闸门，缺一不可，且都由代码强制而非由 agent 自觉遵守（完整论证与实现要求见 [ADR-0002](./adr/0002-ai-never-writes-directly.md)）：

| 闸门 | 要求 | 作用 |
|---|---|---|
| **草稿区** | AI 只写 `draft_*` 表，人确认才由确认动作写事实表 | 任何绕过草稿区的写入路径都是缺陷 |
| **证据链** | 每条草稿挂 `source_id`（哪张截图/哪个文件）+ 原文片段；审核界面原文与解析结果并排 | 把用户的负担从「判断 AI 对不对」换成「扫一眼原文」 |
| **总额交叉校验** | 从一个来源拆出的条目合计，必须与该来源自身声明的合计/余额核对；不符时显式报警并阻止批量入库 | **唯一能在无人工介入下捕获错误的机制，优先级高于解析准确率本身** |
| **审计日志** | append-only，记「谁 / 何时 / 把什么改成了什么」 | 出错时能回溯到具体那一次写入 |

## 5. v1 范围

**原则：「交易」做深，「事项」做薄。**

### 5.1 深：交易

截图导入 → 解析重建 → 证据链 + 总额校验 → 审核 → 入库 → 基础回顾。**做到能真正替代手工流程。**

- 多图批量导入，跨图去重
- 多币种：存**原币金额 + 本位币金额 + 当时汇率**三元组，不要求用户手算（[ADR-0004](./adr/0004-data-model-sqlite-integer-money.md)）
- 商户、分类、渠道
- **审核界面**：密集表格、原文并排、异常项排最前、默认全选、键盘走完。判定标准是 **40 笔 30 秒审完**——整个产品省下的时间全兑现在这一屏
- 基础回顾：这段时间钱花在哪了

### 5.2 薄：事项

一条记录走完整生命周期：`backlog（无日期）→ 排到某天 → 完成（带实际时长）→ 未完成退回 backlog`。**「待办」和「时间日志」是它的两端，不是两个功能。**

- backlog 列表、一句话批量丢入
- 拖到某天、记完成时段
- 能回答「这周时间花哪了 / 什么没做完」

### 5.3 贯穿

- **时间轴是共同骨架，但 UI 分两个视图**——不在同一张日历里混着显示钱和时间
- **记忆系统存规则，不存对话**：商户→分类映射、用户的每次纠正、个人语境词表、语音专有名词表。这是产品唯一的复利——第一个月 40 条改 8 条，半年后 40 条改 1 条
- **交互形态是「对话下指令 + 界面做审核 + 界面看回顾」**，不是聊天框包打天下。语音只用于输入，不用于审核（无法用语音表达「第 7 条金额改成 168」）

## 6. 非目标（v1 明确不做）

| 类别 | 不做的东西 | 说明 |
|---|---|---|
| 事项功能 | 提醒、重复任务、子任务、优先级算法、番茄钟 | 「薄」的字面含义 |
| 采集 | 弱信号采集（git / 日历 / 浏览器历史 / 屏幕使用时间） | 未来做，但必须逐项授权、默认全关（[ADR-0005](./adr/0005-voice-and-system-integration.md)）；届时应接 [ActivityWatch](https://github.com/activitywatch/activitywatch) 而不是自建 |
| 闭环 | 意图↔事实闭环（待办「交房租 2000」被账单里的 2000 转账核销） | v2 方向，见 §11 |
| 数据 | 历史数据导入 | |
| 平台 | 手机端、Windows/Linux 发行 | Tauri 保留后路，v1 只做 macOS |
| 形态 | 任何形式的同步、账号、后端、变现 | 与「本地优先」是同一条约束 |
| 代码 | v1 写任何 Swift | 语音用 macOS 系统听写；sidecar 推 v1.1（[ADR-0005](./adr/0005-voice-and-system-integration.md)） |

## 7. 成功标准

- **一个月**：用它补过 3 次账，**且没有一次因为不放心而回去翻原始截图核对**。开始复核即意味着失败。
- **终点**：不再打开原来的记账软件和日程软件。
- **审核界面单点指标**：40 笔 30 秒审完。

### 9.1 为什么 M0 优先

**M0 验掉产品最大的未知数**：视觉模型读真实银行与支付账单截图到底准不准。这个问题的答案决定整个产品是否成立，必须最先撞。

验证样本用 dogfooding 场景里最难的组合（多渠道、中英文混合、双币种），因为它对解析能力的压力最大——过得了这一关，普通单账户场景不构成风险。

### 9.2 M0 各 sub-PRD 取哪一片

M0 天生横跨多份 sub-PRD——walking skeleton 就是这样。各份取最小切片：

| sub-PRD | M0 切片 | M0 **不**做 |
|---|---|---|
| [`00-foundation`](./prd/00-foundation.md) | SQLite 打开 + 迁移运行器 + `sources` / `draft_transactions` / `transactions` / `audit_log` 四张表 + 错误契约 | 完整 schema、事项相关表、记忆表 |
| [`01-agent-runtime`](./prd/01-agent-runtime.md) | 起 MCP server（stdio）+ spawn `claude -p` + 两个工具（写草稿、查来源） | 可插拔后端的第二个实现、子 agent 上下文隔离 |
| [`02-ingest`](./prd/02-ingest.md) | 拖入单张截图 → 落 `sources` + 证据文件 → 触发一次解析 | 多图批量、跨图去重、文件监听 |
| [`03-review`](./prd/03-review.md) | 一个能看到草稿并逐条确认入库的最朴素列表 | 键盘流、原文并排、异常前置、虚拟滚动 |

## 10. 竞争格局（调研于 2026-08-06）

**「AI 记账」本身不是差异化。** 国内移动端已是红海——账明、一木记账、咔皮记账、AI 记账本、百事 AA 记账，「AI 截图记账 + 语音记账 + 对话分析」全部有人做且免费。

但现有工具（无论国内外）共享两个结构性局限：

1. **都为「当场记录」优化**，把事后重建留给用户手工完成（§1）
2. **都依赖专用解析器**，因而与特定国家的银行/支付平台绑定——这也是为什么国内 app 读不懂澳洲银行对账单、海外 app 不认识微信支付宝。**这不是产品的市场划分，是解析器路线的必然结果**（§3.1）

**海外开源则集体回避 AI**：Actual Budget（本地优先、有 AI 查询）、Firefly III（**官方立场就是「不要黑盒机器学习」**）、ezBookkeeping、CurioPay。这反证了「AI 不敢写账本」是一道真实的坎——本项目的证据链 + 总额校验正是绕过它的路（§4）。

**时间追踪**：[ActivityWatch](https://github.com/activitywatch/activitywatch)（开源、本地优先、跨平台、可写自定义 watcher）是弱信号采集的现成基础设施，**未来应接它而非自建**；它只做「自动采集」不做「人工补录」，也不碰钱——中间那层「把机器活动翻译成人类事项」正是本项目该加的价值。

**结构性差异（对手做不到，不是包装）**：

- 竞品商业模式依赖云，「数据不出本机」做了就没饭吃
- 竞品自付 token 成本，做不起重解析，只能退回专用解析器
- 竞品是记账公司，不做钱与时间同轴

## 11. v2 方向（不进 v1）

待办写着「这周交房租 2000」，账单里出现一笔 2000 转账 → 待办自动打勾、预算自动核销。**意图与事实互相印证**——这是分成两个 app 做不到的事，也是「一个 app」的真正理由。

v1 只需保证数据形状（一条时间轴 + 两个实体）不挡住这条路。

## 12. 已知局限

1. **产品压缩的是整理成本，不是记录意愿。** 用户仍需在当下保留痕迹（截图、留存账单）。做不到这一步的用户，本产品救不了。
2. **时间日志做不到精确时段。** 钱有客观痕迹，时间没有，只能粗粒度——好在时间容忍模糊，钱不容忍。
3. **用户订阅的用量限制是真实约束。** 核心操作（多图 + 长上下文 + 多轮推理）恰好最耗额度。

### 平台风险

Anthropic 对第三方 agent 使用订阅额度的政策反复过：2026-04-04 封禁 → 05 月改为 Agent SDK credits（按 API 价计费）→ **06-15 暂停该改动**（当前 `claude -p` 与第三方应用仍走订阅额度）。方向明确但未落地。

对策是可插拔后端接口（[ADR-0003](./adr/0003-agent-runtime-and-pluggable-backend.md)）。**这是工程对策，不进产品叙事。**
