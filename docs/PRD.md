# Daybook 总 PRD

> Daybook（日簿）是一个跑在本地、**不用逐条填表的 AI 个人事务助理**，把用户零散的钱和事整理成账目与安排。
> **生活可以先发生，记录可以后来补。** 回溯优先是产品的设计原则，不是对外的品类名称。
> 本文定义**做什么、做到什么算成功、明确不做什么**，以及里程碑与各 sub-PRD 的对应关系。**范围变更必须先改本文。**
> 技术选择的完整论证在 [`docs/adr/`](./adr/)；术语定义在 [`docs/CONTEXT.md`](./CONTEXT.md)；系统结构在 [`docs/architecture.md`](./architecture.md)。

---

## 1. 问题

记账工具的设计前提是「交易发生时你会记一笔」。

**这个前提在实际使用中几乎不成立。** 人在付款当下不会掏出 app 记账——排队、赶路、和人说着话。于是记录被推迟，推迟到某个时刻用户坐下来，面对一堆已经模糊的痕迹，试图把过去一两周重建出来。

**现有工具在这一步把用户丢掉了。** 它们为「当场记录」持续优化——快捷输入、桌面小组件、快捷指令、语音速记——却把「事后重建」原样留给用户手工完成：翻银行流水、对截图、逐条敲进去、算汇率、查这笔到底是什么。**补记一次的成本远高于当场记十次**，于是用户放弃，工具沦为装了没用的那一个。

Daybook 的设计前提相反：**默认你是事后补的。** 产品的全部工作是把「重建过去」这件事的成本压到可接受。

但**回溯优先是设计原则，不足以单独解释产品是什么**。Daybook 对外的品类定位是 **AI 个人事务助理**：它接住零散的截图、口述和文字，把其中的交易与事项整理成待确认记录。这里的「个人事务」由 §5 的两个实体限定，不等于完整日历或通用秘书的无限承诺。

### 1.1 逐条填表是痛点的另一半

上面讲的是「事后补记成本高」。但痛点还有一半在当下：**传统工具里创建一条记录要反复完成表单操作**——记账时选账户、分类、金额、商户和日期；安排事项时再填标题、计划日期、时间、截止与状态。摩擦本身就是人放弃持续整理的原因之一。

钱和事被分在记账 app 与日程 / 待办 app 里，但从用户视角看，它们是同一份个人行政负担：**不断把已经发生或准备去做的生活翻译成一个个表单。**

竞品也在打这一半，方式是**做更快的表单**：小组件、快捷指令、语音速记。**我们的解法不同——主路径不要求用户逐条填表。**

| | 竞品的语音速记 | Daybook |
|---|---|---|
| 说一次话 | 记**一笔** | 说一段话，agent 拆成**多笔** |
| 之后 | 仍要确认那一个表单 | **一次批量确认**（见下方脚注） |
| 跨实体 | 不支持 | 一句话里的交易和事项一起处理（[ADR-0003 §2](./adr/0003-agent-runtime-and-pluggable-backend.md) 的论据场景） |

「今天吃饭 180，明天交房租，上周那 400 是给家里买茶叶」——一句话跨多笔、跨实体，说完一次确认完。**竞品做的是更快的表单，我们把一段交代整理成多条待确认记录。**

> **「一次批量确认」不是免检**（2026-08-10 补）。它与 §4 闸门 3 曾经互相打架——[`03-review`](./prd/03-review.md) 让口述来源的总额校验恒为「无法校验」、批量确认必被拒，等于这条差异被自己的闸门挡死了。现结论：**口述来源走一条独立的确认策略**（[03 审核 §3.3](./prd/03-review.md) 的 `confirmation_policy = user_attested_batch`）——允许一次批量确认，**代价是审核界面必须把整段转写原文与全部拆分结果并排展示**，用户按下的那一次确认**就是校验动作本身**。**换了一道闸门，不是少了一道。** 这条只对口述成立，理由是原文是用户自己刚说出口的、他有第一手记忆；截图来源不具备这个条件，**永远拿不到这条策略**。

> **「能不能对账」与「能不能批量确认」是两个维度**（[03 §3.3](./prd/03-review.md)）：口述里若明确说出一条覆盖整段全部适用交易的来源级合计，对账可做，而确认策略仍走用户背书那一档；一张只有一笔、没印合计的截图则相反——对账不适用，但**不因此获得批量放行**。

由此确定五件事：

- **产品定位是 AI 个人事务助理。** 它把钱和事整理成账目与安排；「个人事务」当前只指交易与事项两个实体，功能边界仍由 §5–§6 决定。
- **生活可以先发生，记录可以后来补。** 「回溯优先」是产品设计原则，不再承担对外解释品类的任务。
- **AI 的角色是考古学家，不是输入框。** 从截图等痕迹里把过去还原出来，摆到用户面前，用户只负责审。核心动作是**重建**，不是**录入**。
- **表单不是主路径。** 手工填表只作为 agent 不可用时的兜底与旧记录的编辑入口（[`04-transactions`](./prd/04-transactions.md) §3.5），UI 不给它显眼的入口。
- **产品是低频、重型的**——一两周一次坐下来处理完，不是日常高频工具。但**单条快速录入随时可用**，这两件事不矛盾：低频指的是「补记一整段时间」这个仪式，不是禁止你随口记一笔。

## 2. 用户

**主用户：想把钱和事长期整理清楚、但总被逐条填表劝退的人。**

放弃的原因通常不是没有整理意愿，而是当场记录与事后补记都要求重复操作传统表单。这不是一个小众人群——它同时存在于记账与事项安排里。

**不需要用户具备任何特殊属性。** 「当场记不了、只能事后补」不是用户细分，是使用常态；把它当细分来定位会把问题写小。

**痛感强度随三个维度递增**：账户数 → 支付渠道数 → 币种数。这三项越多，手工整理越不可行，产品的价值越明显。因此多账户 / 多渠道 / 多币种用户是**最先被救到的人群**，也是本项目的**首要验证场景**（多账户 + 多渠道 + 双币种）。

**但这是压力测试场景，不是市场边界。** 产品不依赖任何特定国家、银行或币种——理由见 §3.1：解析能力不认识具体格式，因此天然与地域无关。

v1 不服务：多人协作、家庭共享账本、企业报销。

## 3. 产品原理

三条互相支撑的判断，解释「为什么这个产品现在才可能，以及为什么只能长成这个形状」。

### 3.1 用户自带 AI 额度 → 产品侧边际成本为零 → 可以对任意来源做重解析

传统记账 app 必须为每家银行、每个支付平台写**专用解析器**。这条路线有三个固有缺陷：格式改版就挂、长尾永远覆盖不到、**每进入一个新国家都要重做一遍**。按 API 计费的竞品即使用了模型，算完 token 账也会退回去写解析器。

自带额度让「对着任意截图直接说读吧」成为可能。**这条能力天然与银行、币种、国家无关——因为它根本不认识具体格式**，也就无从被格式局限。多币种、多渠道、任意版式都是这一条的自然结果，不需要为它们单独设计。

**「边际成本为零」说的是产品侧，不是用户侧**（2026-08-09 澄清）：token 记在用户自己的订阅或 API 账户上，所以本项目不需要为解析量付钱、也不需要为它设计计费。用户那边不是零——额度有限、超出可能产生费用，且第三方应用经 `claude -p` 调用同样消耗订阅用量。**因此重解析虽然便宜到可以随便用，但不能替用户宣称它免费**，UI 与文档都不该这么写。

### 3.2 用户已安装的 agent CLI 就是成熟的 agent runtime

Claude Code、Codex 本身已具备多轮推理、工具调用、上下文管理。产品需要的是「下达任务、它自己编排」，而不是「一个能调 API 的输入框」。

这也是**必须做成桌面应用**的理由：要调用本机登录态、本机进程、本机文件（[ADR-0003](./adr/0003-agent-runtime-and-pluggable-backend.md)）。

### 3.3 本地优先：无 Daybook 账号、无远程服务端、不托管用户数据

账目与日程极私密。这一条要分两件事说，混在一起就会自相矛盾（2026-08-09 澄清）：

**持久化**——账本、证据文件与日志**全部存在用户本机**的应用数据目录，用户看得见、能自己删。**不存在 Daybook 账号、远程服务端、云同步、遥测或崩溃上报**，本项目不运行任何远程服务，因此无服务器成本、无用户数据托管责任。这也是一个人能长期维护的唯一形态（[ADR-0001](./adr/0001-local-first-desktop-platform.md)）。

**传输**——解析依赖用户自己安装并登录的 agent CLI，而 **`claude -p` / `codex exec` 这类 CLI 的推理跑在其模型服务商那边**。解析一张截图时，**该截图与相关文本会由该 CLI 发往它对应的服务商**，用的是**用户自己**在那家服务商的订阅与登录态。这条链路由 CLI 自己发起，**本应用不代理、不转发、不记录**，也**不产生任何 Daybook 侧的存储**——但它确实存在。

因此对外的正确表述是：

> 账本、证据与日志由 Daybook 本地存储；解析所需的内容会由用户选择的 agent CLI 发往其模型服务商。**无 Daybook 账号、无远程服务端**，不代理流量、不收集遥测、不托管任何用户数据。

**三条措辞纪律**：

1. **不要写「数据不出本机」而不加限定**——这在本产品的架构下是错的，而且是那种被用户发现一次就再也不信第二句的错。仓库内部沿用它作为**约束口号**（[`CLAUDE.md`](../CLAUDE.md) 约束 2 带完整例外条款）没问题，**对外文案不行**。
2. **不要写裸的「无服务器」「无后端」**——本产品自己就有一个**本机 MCP server**，还有一个叫「**agent 后端**」的抽象接口，两者都在本机内部、都不是远程服务。裸说「无 server / 无 backend」会和自己的术语打架。要说就说全：**无远程服务端、不托管用户数据**。
3. **不要写「无账号」**——用户必须在模型服务商那边有账号并已登录，否则 CLI 跑不起来。准确的是：**无 Daybook 账号**。

若用户使用的是本地模型后端（[ADR-0003](./adr/0003-agent-runtime-and-pluggable-backend.md) 的可插拔接口之一），**解析内容就无需发往任何远程模型服务商**。**但不要因此说「没有任何出站流量」**——那个本地模型进程自身会不会联网（检查更新、上报使用情况）取决于它的实现与配置，**不在本应用的控制范围内，也担保不了**。**这是用户所选后端的属性，不是产品的默认承诺**。

## 4. 数据可信性：AI 永不直接写入账本

视觉模型会把 168 读成 1680。账本与普通 AI 应用的差别在于错误的性质：**账本错一个数字，用户信任就永久归零，且不可逆**——一旦用户开始回头核对原始截图，产品声称节省的时间就全部吐了回去。

四道闸门，缺一不可，且都由代码强制而非由 agent 自觉遵守（完整论证与实现要求见 [ADR-0002](./adr/0002-ai-never-writes-directly.md)）：

| 闸门 | 要求 | 作用 |
|---|---|---|
| **草稿区** | AI 只写 `draft_*` 表，人确认才由确认动作写事实表 | 任何绕过草稿区的写入路径都是缺陷。**这条的前提是 agent 子进程以密封配置启动且有效工具集经过实测**——通用 CLI 自带的内置工具能直接绕过它（[01 §3.7](./prd/01-agent-runtime.md)） |
| **证据链** | 每条草稿挂 `source_id`（哪张截图、哪个文件，**或哪段口述文本**）+ `evidence_text`；审核界面把**来源原件**与解析结果并排 | 把用户的负担从「判断 AI 对不对」换成「扫一眼原件」。**`evidence_text` 是 agent 的抽取声明，不是独立证据**——它和被核对的金额出自同一次模型输出（[ADR-0002 闸门 2](./adr/0002-ai-never-writes-directly.md)） |
| **总额交叉校验** | 从一个来源拆出的条目合计，只与一条覆盖**当前不可变来源全部适用交易**的声明合计核对（不是账户余额；合计连类型一起存；月度 viewport 外、分页、按日 / 分类 / 单笔语义 / 子组合计不得报告，见 [ADR-0002 闸门 3](./adr/0002-ai-never-writes-directly.md)）；不符时显式报警。`kind = file` 不符或无法校验时 `confirmation_policy = single_only`、拒绝批量；`utterance` 由 `user_attested_batch` 的人工背书闸门决定 | **唯一能在无人工介入下捕获错误的机制，优先级高于解析准确率本身**。对结构性通常没有合计的口述来源换人工闸门，**不是取消**（§1.1 脚注） |
| **审计日志** | append-only，记「谁 / 何时 / 把什么改成了什么」；**agent 的原始起草值不可变** | 出错时能回溯到具体那一次写入，以及「AI 当初写的是什么」 |

## 5. v1 范围

**原则：「交易」做深，「事项」做薄。**

### 5.1 深：交易

截图导入 → 解析重建 → 证据链 + 总额校验 → 审核 → 入库 → 基础回顾。**做到能真正替代手工流程。**

- 多图批量导入，跨图去重
- **语音/文字一句话记多笔**（§1.1）：说一段话 → agent 拆成 N 条草稿 → 一次批量确认。语音在本机转写，v1 用 macOS 系统听写（[ADR-0005](./adr/0005-voice-and-system-integration.md)）
- 多币种：存**原币金额 + 本位币金额 + 当时汇率**三元组（各带币种标识），不要求用户手算（[ADR-0004](./adr/0004-data-model-sqlite-integer-money.md)）。**本位币可切换**，逐笔冻结
- 商户、分类、渠道
- **审核界面**：密集表格、原文并排、异常项排最前、默认全选、键盘走完。判定标准是 **40 笔 30 秒审完**——整个产品省下的时间全兑现在这一屏
- 基础回顾：这段时间钱花在哪了

### 5.2 薄：事项

**事项是同一条记录的「计划」与「结果」两端**，不是待办与时间日志两套实体。状态为 `backlog / scheduled / done / archived`：没有计划时在 backlog；有计划时 scheduled；用户明确确认后 done；明确放弃时 archived。过期不自动改期或退回，完成与归档都可由用户显式纠正。

- **计划与结果分层**：可记录不定时日期、时间点、最长 24 小时且可跨一次午夜的时间块，或不推断每日活动的粗粒度日期范围；结果只存用户明确报告或确认的变化，未报告字段显示时回退计划值但不复制成事实
- **截止独立**：截止日期与可选截止时间不等于计划，不自动安排、不触发提醒
- **自然语言是主路径**：一段话可批量新建事项、修改已有事项或补记已完成事项；agent 只产出带来源与字段差异的待确认草稿，目标匹配失败时不得静默新建
- **周视图做精调与回顾**：截止、跨日、不定时、小时格、未安排、待处理六个区域；拖拽/拉伸是人的确定性修改，立即生效、可撤销、写审计；冲突只呈现，不替用户解决
- **单清单分组**：每个事项最多属于一个用户自定义清单，不做多标签、层级或优先级
- 回顾回答「完成了什么 / 什么没做完 / 什么要重新安排 / 什么即将截止」，不以稀疏的自报数据生成每周实际用时汇总

完整时间语义、状态转移与验收见 [05 事项](./prd/05-items.md)。

### 5.3 贯穿

- **时间轴是共同骨架，但 UI 分两个视图**——不在同一张日历里混着显示钱和时间
- **记忆系统存规则，不存对话**：商户→分类映射、用户的每次纠正、个人语境词表、语音专有名词表。这是产品唯一的复利——第一个月 40 条改 8 条，半年后 40 条改 1 条
- **交互形态是「对话下指令 + 界面做审核 + 界面看回顾」**，不是聊天框包打天下。系统听写可以形成事项的新建或修改指令，但不能完成最终确认、不能让 agent 直接写事实；交易金额与事项目标/字段差异仍须在界面中精确审核（无法只靠语音可靠表达「第 7 条金额改成 168」）
- **首次启动必须如实告知数据去向**（2026-08-10 新增）：§3.3 定了对外措辞的纪律，但那管的是 README 和文档——**用户在应用里也必须看到同一件事**，而且是在他把第一张截图拖进来**之前**。一屏说清三件事：① 账本、证据与日志只存在本机，位置在哪、他能自己删；② **解析时截图与文本会由他自己的 agent CLI 发往对应的模型服务商**，用的是他自己的订阅；③ 应用不代理、不转发、不记录，也没有 Daybook 账号。**不是勾选同意书，是一次说明**——但它必须存在。理由与 §4 同源：**用户发现产品对数据去向说得不全，信任归零的速度和发现账目错了一样快。** 落点是 [01 Agent 运行时](./prd/01-agent-runtime.md) 的人工验收

## 6. 非目标（v1 明确不做）

| 类别 | 不做的东西 | 说明 |

### 9.1 为什么 M0 优先

**M0 验掉产品最大的未知数**：视觉模型读真实银行与支付账单截图到底准不准。这个问题的答案决定整个产品是否成立，必须最先撞。

验证样本取最难的组合（多渠道、中英文混合、双币种），因为它对解析能力的压力最大——过得了这一关，普通单账户场景不构成风险。

**M0 同时验第二个未知数**（2026-08-08 加入）：**一段口述能不能被可靠地拆成多笔**。§1.1 把录入摩擦确认为痛点的另一半，而「一句话拆多笔」是我们相对竞品语音速记的唯一差异——它和视觉解析一样是未经验证的能力，同样该在 M0 撞。

两个未知数共用同一条下游链路（草稿 → 闸门 → 审核 → 入库），所以第二个的边际成本很低：一列 `sources.kind`、一个输入框、一份提示词模板。

### 9.2 M0 各 sub-PRD 取哪一片

M0 天生横跨多份 sub-PRD——walking skeleton 就是这样。各份取最小切片：

| sub-PRD | M0 切片 | M0 **不**做 |
|---|---|---|
| [`00-foundation`](./prd/00-foundation.md) | SQLite 打开 + 迁移运行器 + `sources` / **`parse_attempts`** / `draft_transactions` / `transactions` / **`accounts`（骨架）** / `audit_log` **六张表** + 错误契约 + 币种 exponent + 金额过 IPC 的字符串约定 | 完整 schema、`accounts` 的字段与 UI（M2）、事项相关表、记忆表 |
| [`01-agent-runtime`](./prd/01-agent-runtime.md) | 起 MCP server（stdio）+ **以密封配置** spawn `claude -p` + **有效工具集探测**（[01 §3.7](./prd/01-agent-runtime.md)）+ **五个工具**：`list_pending_sources` · `read_source` · `draft_transaction` · `report_source_total` · **`complete_source`**（清单见 [01 §3.2](./prd/01-agent-runtime.md)） | `draft_item` / `query_memory`（目标表 M0 未建，推 M3）、可插拔后端的第二个实现、子 agent 上下文隔离 |
| [`02-ingest`](./prd/02-ingest.md) | 拖入单张 PNG/JPEG 截图 → 落 `sources` + 证据文件 → 触发一次解析。**外加 `kind = utterance` 来源**：一段口述/文字 → agent 拆成 N 条交易草稿 | HEIC / PDF（推 M2）、多图批量、跨图去重、文件监听 |
| [`03-review`](./prd/03-review.md) | 一个能**看到来源原件**、看到每条的 `evidence_text` 与声明合计、并逐条/批量确认入库的最朴素列表；四道闸门全部生效 | 键盘流、异常前置排序、虚拟滚动。证据图区域高亮原属待 spike 项，已于 2026-08-24 实测否决（[03 §5](./prd/03-review.md) R1） |

> **M0 的语音只记交易。** `draft_items` / `items` 是 M3 的表（[00 地基 §3.6](./prd/00-foundation.md)），所以 M0 里 agent 听到「明天交房租」这类**事项**内容时**必须明确回一句「这条我现在还记不了」**，不得静默丢弃。把事项表提前到 M0 会显著扩大 M0，明确不做。
>
> **闸门 3 对 utterance 通常不适用，但不是「恒不适用」**（2026-08-30 补 scope）：一段口述一般没有来源级聚合，此时 `parse_attempts.reported_total_*` 为空、对账结果 `not_applicable`。只有用户说出的合计覆盖整段当前来源全部适用交易时才照常对账；月度外部范围、单笔或子组「总共」仍不得报告（[00 地基 §3.6](./prd/00-foundation.md)）。
> **无论哪种，确认策略恒为 `user_attested_batch`**——这正是把两个维度拆开的意义。**不等于少一道闸门**：批量确认换成了「整段原文与全部拆分结果并排 + 一次人工确认」，见 §1.1 脚注。`03` 的异常前置排序仍会把这类草稿单独提一档。

> **`report_source_total` 为什么在 M0**：没有它就没有 `parse_attempts.reported_total_minor`，[总额交叉校验](./adr/0002-ai-never-writes-directly.md)（闸门 3）无从成立。M0 的目的是验证端到端链路**连同四道闸门**是否立得住，抽掉一道闸门的 M0 验不出该验的东西。
>
> **`complete_source` 为什么在 M0**（2026-08-10 加入）：没有它，「解析完成」的唯一判据是子进程退出码——而 agent 读了 12 笔里的 9 笔再正常收工，退出码同样是 0。**静默漏读是这类模型最典型的失败模式，而它恰好是 M0 要撞的两个未知数之一**；总额校验也挡不住（漏读的那几笔如果连合计也没读到，结果只是「无法校验」）。见 [01 §3.2](./prd/01-agent-runtime.md)。
>
> **`03` 的「原件可见」M0 就要有**（2026-08-10 收紧）：M0 只渲染 `evidence_text` 那一列是不够的——它和被核对的金额**出自同一次模型输出**，模型把 168 读成 1680 时也会把它写成「1680」，用户核对的是模型和它自己。**M0 的最小形态是「原图缩略图 + 点击看原图 + `evidence_text` 同屏」**，一个 `<img>` 的成本。M0 当时只把区域高亮留给 [03 §5](./prd/03-review.md) R1 spike，**不是推迟原件本身**；该 spike 已于 2026-08-24 证明 agent 坐标会误指相邻行，因此 M1 也不加伪精确高亮，继续使用完整原件 + `evidence_text` 的安全退路（[实测](./spikes/2026-08-24-r1-evidence-region.md)）。

### 9.3 M0 的端到端判定：`scripts/verify-m0.mjs`

[`01`](./prd/01-agent-runtime.md)、[`02`](./prd/02-ingest.md)、[`03`](./prd/03-review.md) 三份 sub-PRD 都把这个脚本列为验收标准，因此**它验什么必须在这里定义**——否则 M0 的判定标准就是个黑盒（2026-08-07 M0 开工评审补定）。

脚本在一个**临时数据目录**上跑完整链路，退出码非零即失败：

| # | 检查 | 判据 |
|---|---|---|
| 1 | 迁移 | 空目录启动后**六张** M0 表存在（含 `accounts` 骨架），`user_version` 等于最大迁移号；`PRAGMA foreign_keys = ON` 下插入 `account_id IS NULL` 的交易成功 |
| 1b | **未知币种** | 用一个不在 ISO 4217 表内的币种码起草 → 被拒（`data.unsupported_currency`），**不写库、不回退到两位小数**（[00 §3.4](./prd/00-foundation.md)） |
| 2 | 导入 | 投入一张固定的测试截图 → `sources` 恰好一行，`state = imported`，证据文件存在且 SHA-256 与输入相等 |
| 3 | 幂等 | 同一文件再投一次 → 仍是一行，返回 `deduplicated: true` |
| 3b | **工具集密封** | 下发任务前的探测返回的有效工具集**恰好等于** [01 §3.2](./prd/01-agent-runtime.md) 的五个，且该清单来自**结构化 introspection**（不是问模型）；人为放开一项 → 返回 `agent.tool_surface_unsealed` 且不下发任务（[01 §3.7](./prd/01-agent-runtime.md)） |
| 4 | 解析 | 触发解析 → `state` 走到 `parsed`，`parse_attempts` 恰好多一行且 `outcome = "completed"`，`draft_transactions` 行数 > 0，**每行 `source_id` / `evidence_text` / `drafted_json` / `source_ordinal` 非空**，且 ordinal 在本次尝试内不重复 |
| 4b | **完成协议** | 让 agent 不调 `complete_source` 直接退出 → `outcome = "protocol_violation"`，来源转 `failed`，草稿 `voided_at` 非空，**`state` 不为 `parsed`**（[01 §3.2](./prd/01-agent-runtime.md)） |
| 4c | **条目数不符可补救** | 让 agent 自报的条目数比实际多一条 → 首次 `complete_source` 返回 `agent.completion_mismatch` 且**会话未封闭**；补起草后再调成功，`outcome = "completed"` |
| 4d | **重试不串台** | 让第一次解析超时后重试 → `parse_attempts` 两行，校验用的是**第二行**的 `reported_total_*`，且求和只含第二次的草稿（[03 §3.3](./prd/03-review.md)「入参是 `attempt_id`」） |
| 5 | 审计 | 每条草稿对应一条 `actor = "agent"` 的 `audit_log` |
| 6 | 闸门 | 篡改一条草稿金额使合计不符 → 批量确认返回 `review.total_mismatch`，`transactions` 仍为空 |
| 6b | **校验不随确认漂移** | 在第 6 步的 `failed` 状态下逐条确认掉一条 → **再次校验结果仍为 `failed`**，不因已消费条目退出求和而改变（[03 §3.3](./prd/03-review.md)） |
| 7 | 确认 | 改回正确金额 → 批量确认成功，`transactions` 行数等于草稿数，每行 `source_draft_id` 指回原草稿且草稿 `consumed_at` 非空；**被改过的那条草稿 `drafted_json` 仍是 agent 当初写的值** |
| 8 | 隔离 | 全程 `transactions` 的写入只发生在第 7 步（确认动作），MCP 工具调用期间恒为空 |
| 9 | **语音路径** | 投入一段固定文本（模拟转写结果）→ `sources` 多一行且 `kind = utterance`、本次尝试 `reported_total_*` 为空 → 拆出 ≥2 条交易草稿，每条 `evidence_text` 是该文本的对应片段 → `reconciliation_status = not_applicable` 且 `confirmation_policy = user_attested_batch`（**不是 `unavailable` / `single_only`**）→ **一次批量确认成功入库**（2026-08-10 改：此前这里写「批量确认被拒」，与 §1.1 的产品承诺冲突） |
| 10 | **口述不误去重** | 同一段文本**配新的提交令牌**再投一次 → `sources` **多一行**（`deduplicated: false`）；配同一个令牌再投 → 仍是一行（[02 §3.2](./prd/02-ingest.md)） |
| 11 | **崩溃恢复** | 预置一条 `state = parsing` 的来源与一行 `ended_at` 为空的 `parse_attempts` → 启动扫描把两者分别转为 `failed` / `interrupted` 并作废草稿（[02 §3.4](./prd/02-ingest.md)） |

**验证分两层，且两层都必须通过。** 第 4b、4c、4d、6、6b、7、8、11 步使用仓库内的**确定性脚本后端**驱动同一条外部进程 / stdio MCP / UDS / 数据库链路，使协议失败、超时、条目数不符与篡改金额等负路径可稳定复现；第 3b、4、9 步另用**真实且已登录的 agent CLI**验证密封能力探测、截图 happy path 与口述 happy path。检测不到真实后端时脚本以非零退出并明确报错，**不把脚本后端的通过冒充为真实 CLI 通过**。

**验收选择器与 status 同步**（2026-08-17 补）：`scripts/verify-m0.mjs` 只要求 `status: in-progress | review | done` 的 sub-PRD 所列 `cargo test` / `npm test` 选择器已经命中真实测试；`draft` / `ready` / `blocked` / `archived` 跳过。理由是 [`docs/prd/CLAUDE.md`](./prd/CLAUDE.md) 的生命周期先有 `ready` 规格、再批准并开始实现——在 `ready` 阶段强制测试已经存在，会让规格无法先于实现。脚本遇到未知 status 或把全部文档都跳过时仍须失败，避免状态解析坏掉后得到假绿；一旦转 `in-progress`，当前里程碑的选择器必须随首个实现提交落地。

第 9 步用固定文本而非真实语音：转写由 macOS 系统听写完成、音频不出本机、应用零代码（[ADR-0005 §1](./adr/0005-voice-and-system-integration.md)），所以脚本的被测对象是「文本 → 多笔草稿」这一段，转写本身不在测试范围。

### 9.4 M0 的 go / no-go（2026-08-10 新增）

**§9.3 验的是「链路通不通」，不是「读得准不准」。** 但 §9.1 说得很清楚，M0 存在的理由是撞两个未知数——**视觉模型读真实账单准不准**、**一段口述能不能可靠拆多笔**。「跑通一张图」通不过这个考试：一张图跑通了而二十张里错了六张，产品照样不成立，而链路脚本会全绿。

**因此 M0 结束时必须有一轮真实样本的度量，并对着阈值给出 go / no-go。**

这次结果证伪了 [00 地基](./prd/00-foundation.md)、[01 Agent 运行时](./prd/01-agent-runtime.md)、[03 审核与草稿区](./prd/03-review.md) 与 [07 评测](./prd/07-eval.md) 的合计范围 / 正式报告契约，四份已按 [`docs/prd/CLAUDE.md`](./prd/CLAUDE.md) 退回 `draft`。**M1 不得开始**，先完成 M0 no-go 修正、零额度门禁与独立样本复测。

**样本量**：**20–30 张截图 + 20 段口述**。截图覆盖不同版式与至少两种币种；口述覆盖不同长度、语序倒装、省略主语、口语数字（「一百八」「180」「一百八十块」）。**样本采集与标注就是 [07 评测](./prd/07-eval.md) 的 eval 集起点**，不是一次性工作。

**指标与阈值**（**全部是初值，M0 实测后校准并回流本节**——同 [01 §5](./prd/01-agent-runtime.md) R1 的 180 秒是怎么定的）：

| # | 指标 | 阈值（初值） | 为什么是它 |
|---|---|---|---|
| 1 | **条目 recall**（漏读率的反面） | ≥ 0.98 | 漏读是最危险的错误：**用户看不见不存在的东西**。总额校验只在有合计时挡得住 |
| 2 | **条目 precision**（多读/幻觉） | ≥ 0.98 | 多读能被用户一眼看出并丢弃，危害低于漏读，但高于分类错 |
| 3 | **金额 + 币种 + 日期的逐字段准确率** | ≥ 0.98 | 这三项错了就是「168 读成 1680」那类不可接受的错 |
| 4 | **声明合计的可获得率**（全部 `file` 来源中，scope-valid claim 实际得到 `passed` 或 `failed` 的比例） | ≥ 0.70 | 闸门 3 的实际覆盖面。低于此，「唯一的自动纠错机制」在多数来源上根本没启动 |
| 5 | **总额校验的假警报率**（校验 `failed` 但人工核对后 agent 其实读对了） | ≤ 0.05 | **假警报比不报警更伤**——它训练用户忽略报警 |
| 6 | **口述的静默遗漏率**（说了 N 件、拆出 < N 件且未在 `unparsed_note` 里说明） | ≤ 0.02 | 这是「一句话拆多笔」这条差异化能否成立的判据 |
| 7 | **人工纠正率**（需要改的条目 / 全部条目） | ≤ 0.20 | §5.3 的复利叙事从「40 条改 8 条」起步，这就是那个 8 |
| 8 | **干净来源率**（口径见下，**不是「一个字都没改」**） | ≥ 0.60 | 见下方——**这一条比 1–3 更贴近用户感受**，不能只看池化平均 |
| 9 | **单来源耗时** | ≤ 180 秒 | 与 [01 §5](./prd/01-agent-runtime.md) R1 的硬超时同一个数 |
| 10 | **单来源额度消耗** | 记录，**不设阈值** | 无先验可定阈值。M0 的任务是**测出来**，供 [07 §5](./prd/07-eval.md) R3 判断 eval 跑得起跑不起 |

> **为什么必须有第 8 条这个来源级指标**（2026-08-10 补）：**池化平均会藏住用户真正感受到的东西。** 500 条里错 10 条，池化 recall 是 0.98，看起来漂亮；但如果那 10 条散落在 10 个不同来源上，30 个来源里就有 10 个是脏的——**用户体验到的是「每三次导入就有一次要我去翻原图」**，而不是「准确率 98%」。§7 的成功标准写的是「没有一次因为不放心而回去翻原始截图」，它衡量的单位本来就是**一次导入**，不是一行记录。

**「干净」的口径，采样前冻结**（2026-08-10 定死——**不冻结的话不同人会算出不同的 0.60**）。一个来源算「干净」，当且仅当同时满足：

| 计入 | 不计入 |
|---|---|
| **无漏读、无多读**（条目集合与期望一致） | `category` —— 它由记忆规则演进，不是解析能力（[07 §3.3](./prd/07-eval.md) 已把它排除在分数外） |
| `amount_minor` 全对 | `channel` —— 同上，且 M0 本来就不要求它非空 |
| `currency` 全对 | `merchant` 的文案差异（门店号、大小写、多余空格）—— 判据是 [07 §5](./prd/07-eval.md) R1 待决，**没定之前不能拿它当门槛的一部分** |
| `occurred_on` 全对 | `note` 等纯自由文本 |
| `direction` 全对 | |

**一句话**：**M0 的「干净」= 条目完整 + 那四个硬字段全对。** 分类与商户文案的改动**不算脏**——它们本来就是记忆系统要在 M3 之后消化的东西（§5.3 的复利），把它们算进 M0 的门槛，等于用一个 M3 才开始工作的机制去卡 M0。

> **这个口径会让第 8 条比直觉宽松**，是有意的：它衡量的是「**这次导入我需不需要回去翻原图**」，而不是「我一个字都没动过」。用户改一下分类不会去翻原图，金额对不上会。

#### 另外四条口径，同样采样前冻结（2026-08-16 补）

上面冻结的是第 8 条。**另有四处「同一个数字怎么算」本节此前没写死**，不写死则不同实现会算出不同的结果——与第 8 条当初要防的是同一件事。**十项阈值的数字一个未动**，这里补的全是口径：

| # | 口径 | 为什么必须现在定 |
|---|---|---|
| ① | **指标 1–3 按截图池与口述池分开算，两池各自过阈值** | §9.1 的两个未知数（视觉模型读账单准不准、一段口述能不能可靠拆多笔）本来就是**独立的两件事**。合成一个池子，其中一个的失败会被另一个的成绩盖住，而 M0 存在的理由正是分别撞这两个未知数 |
| ② | **指标 7（人工纠正率）的「需要改」与第 8 条同口径**——只算四个硬字段与漏读多读，`category` / `channel` / `merchant` 文案不计入 | 两条指标在量同一件事（这次导入脏不脏），用两套分母会得到两个互相矛盾的结论，而报告上看不出它们口径不同 |
| ③ | **每条用例 1 轮出正式数**；不达标的条目另跑 3 轮，结果只进诊断栏、**不改正式结论** | 多跑几轮挑一个好看的写进报告，与看完答卷再改阈值是同一种作弊，只是换了个位置 |
| ④ | **指标 4（声明合计可获得率）的分母只含 `kind = file`** | 口述来源不走机器对账（[03 审核 §3.3](./prd/03-review.md)），混进分母会把这个数稀释成量不到闸门覆盖面的东西——而它量的就是闸门 3 的覆盖面 |

**聚合边界同样冻结**（2026-08-24 补）：指标 1–3 只在截图池 / 口述池各自聚合；指标 4–8 在两池的**正式判定集合**上聚合，其中指标 4 只取 `kind = file`、指标 5 的分母是两池里**实际出现 `reconciliation_status = failed` 的全部来源**、指标 6 只取 `kind = utterance`。对照栏只记录，永不进入任何正式分子或分母；指标 9–10 只记录逐来源观测值，不参与 verdict。把 4–8 分别算在两池会制造两套不存在于本节的阈值判定，属于口径错误。

**每个比率一律连原始计数一起报**，写成 `0.967 (58/60)`。小分母上的比率是量化的：60 条上 `≥ 0.98` 实际等于「最多漏 1 条」，漏 2 条直接掉到 0.967。**判定仍机械按阈值走**，但报告必须让「差一条」和「差五条」一眼可辨——否则事后没人说得清那个数是怎么来的，而下面那条防滥用流程的第 3 步恰恰要求说得清。

#### M0 的单一声明合计范围与零容忍契约（2026-08-30 新增）

M0 继续接受**任意 viewport 的截图**：来源边界是导入后不可变的那份截图 / 转写文本，不要求整页、整月或完整账单。`report_source_total` 在 M0 只支持**一条**声明合计，且该合计必须精确覆盖当前不可变来源中的**全部适用交易**：`expense_total` 覆盖其中全部支出，`income_total` 覆盖其中全部收入，`net_change` 覆盖其中全部收入与支出。合计若还覆盖 viewport 外的月度交易、其他分页，或只覆盖按日 / 分类 / 单笔 / 其他子集，即为 **scope-invalid**，不得报告；多个局部 claim 也不得挑一个硬塞进单 claim 字段；若有效总计与 invalid decoy 恰好拥有同一 amount/currency/kind 三元组，现有四列无法审计身份，M0 保守地都不报告。合计词只是候选信号，不构成「必须报告」的证明。

这条不提前实现多 claim 生产 schema：`parse_attempts.reported_total_*` 四列与 M0 五工具不变。正式评测在 `expected.json` 中独立标注合计范围资格；`eligible` 还必须列出 bounded `candidateClaims`、固定 expected claim 的 amount/currency/kind 身份，并保证该三元组在候选中唯一，并增加一条不属于十项阈值的 transcript 硬契约：**scope-invalid 合计成功报告数必须为 0；来源有有效总计与 decoy 小计时，错报 decoy 同样计入；大于 0 即 no-go。** 指标 4 的分母仍是正式截图池全部 `kind = file` 来源、阈值仍是 `≥ 0.70`；其分子只承认与 expected claim exact 匹配且实际得到 `passed` / `failed` 的来源，不能靠局部合计抬高覆盖率。

**beachhead 与样本构成同批冻结**，见 [07 评测 §3.4](./prd/07-eval.md)「M0 go / no-go 的样本构成」：beachhead = 交易列表类截图；非 beachhead 来源（单笔小票、月结单）采 3–5 张进对照栏、如实报数但不参与判定；口述定长度分布。**那一节是样本构成的权威出处，本节是阈值与口径的权威出处**，两边不复述对方。

#### 正式判定命令、两阶段人工裁定与诊断

**只有 `node scripts/eval.mjs --m0-go-no-go --manifest <fixtures/local/.../manifest.json>` 能产生本节的正式 verdict。** `node scripts/eval.mjs` 不带参数仍保留为 ad-hoc live 兼容入口，`--replay` 仍只测闸门；两者的报告无论显示什么数字，都不是 M0 go / no-go。正式 manifest 保持 `version: 1`，在既有字段上增加可选 `profile` / `sample` 元数据；普通 dry-run、replay 与 ad-hoc live 对旧 manifest 向后兼容，只有 `--m0-go-no-go` 强制 [07 评测 §3.4](./prd/07-eval.md) 的样本构成、`fixtures/local/` 路径、来源类型 / 长度分层、中性 case ID、合计范围资格与口述 ordinal 标注契约。

正式 first / final 报告必须额外持久化三类可审计证据：① 覆盖 manifest、每个启用 case 的 `expected.json` / `env.json` / 实际输入字节的完整 `fixtureSetSha256`；② 每个错误、漏读与多读条目的 expected / predicted 四硬字段值；③ 每个 case 的合计范围资格、expected claim 身份、agent 报告值 / 身份匹配结果、代码计算值、差额与**最多 160 个 Unicode code point** 的合计证据摘录（附原长度与是否截断）。真实文本只能存在被忽略的 `output/` 与 `fixtures/local/`；仓库内 CI 回归一律使用合成内容。字段与规范化哈希算法的完整契约见 [07 评测 §3.4/§3.5](./prd/07-eval.md)。

**指标 5 必须走两阶段**，因为「校验 `failed` 但 agent 其实读对了」只能由人对原件裁定：

1. 首轮正式运行每例恰好 1 轮，报告写到本机持久路径并且不覆盖；若存在待裁定的 `failed` 来源，正式状态是 `incomplete`，退出码 2。首轮报告永久保留，不能在裁定后改写
2. 工具在首轮报告旁生成独立 `adjudications` 模板；人只在该文件里逐例写「假警报 / 真警报」
3. `node scripts/eval.mjs --m0-finalize <首轮报告>` 只读首轮报告与独立裁定文件，**零额度、不重跑 agent**，另写一份 final 报告并给出 verdict

**三轮诊断不救正式分数。** `node scripts/eval.mjs --m0-diagnose <首轮报告>` 的目标集合是「首轮未达到干净口径的 case」与 manifest 里预标 `flaky` 的 case 的并集；每例**追加 3 轮**，写独立诊断报告。诊断报告不得覆盖首轮 1 轮的指标、不得改首轮 / final verdict，也不得因某轮成功而挑最好的一轮回填。

**正式运行不自动重试。** 单例的模型输出 / 完成协议等 case 质量失败要记进报告并继续后续 case；后端不可用、额度耗尽、进程启动失败、本地读写失败等运行或基础设施错误可以中止整轮，避免把一份残缺运行冒充完整样本结果。

**正式退出码固定**：`0 = go / conditional-go`、`1 = 运行或基础设施错误`、`2 = incomplete`（例如指标 5 待人工裁定）、`3 = no-go`。这些码只属于 `--m0-go-no-go` / `--m0-finalize` 的正式流程；ad-hoc live 保持原兼容行为。

**判定**：

- **指标 5 仍有待人工裁定 ⇒ incomplete。** 先保存首轮报告，不能用暂缺的分子伪装成 0
- **1–3 任一不达标 ⇒ no-go。** 这三条是产品可信性的地板，达不到就不是「再优化一下提示词」的问题，而是 §3 的三条产品原理里有一条不成立
- **4–8 不达标 ⇒ 条件 go**：允许进 M1，但**必须在里程碑表里记下是哪一条、对策是什么**，不许默认它以后会自己好
- **9–10 只记录**

> **这些阈值不是从行业基准来的，是从产品定义倒推的**：§7 的成功标准是「补过 3 次账且**一次都没回去核对原始截图**」。用户一旦发现一处错，就会开始复核，产品当场失败。0.98 是「40 条里错不到 1 条」——**再低一档就是每次都有错**。

#### 阈值可以改，但不能在看完答卷之后改（2026-08-10 补）

**「初值，实测后校准」这四个字有一个明显的滥用方式**：跑完第一批样本 → 发现 recall 是 0.94 → 把阈值调到 0.93 → 宣布通过。**那不是校准，是移动门柱**，而且它会把 M0 这道关卡变成一次形式。

**流程固定为四步，顺序不可换**：

1. **先定 beachhead 来源类型与样本构成**，**再去采样**——不是先看有什么样本再定测什么。**✅ 2026-08-16 做完**：beachhead = 交易列表类截图，[07 评测 §5](./prd/07-eval.md) R8 随之关闭；构成见 [07 评测 §3.4](./prd/07-eval.md)「M0 go / no-go 的样本构成」，同批冻结的四条阈值口径见本节「另外四条口径，同样采样前冻结」
2. **用第一批样本、按上表的原阈值，给出正式结果。✅ 2026-08-29/30 做完：`no_go` / exit 3。** 这个结果与 `fixtures/local/m0-2026-08-24` 永久保留，**不因为标注缺陷或规格修正而作废、改写或重新解释**
3. **要改阈值，先写清为什么**：是这条指标度量的东西本身有问题，还是产品对它的要求变了。**「达不到」不构成理由。当前修正不改任何阈值、指标 4 分母或 ordinal full outer join**
4. **修正后的规格与实现用第二批独立新样本验证**，不复用第一批。第一次样本只作 challenge / regression；修正后的真实真值写进新的 `fixtures/local/` ignored 样本集

**这条纪律和 §4 的四道闸门同源**：闸门存在的意义是它有可能拦住你；一个跑不出「不通过」的判定标准，和一个永远显示通过的总额校验一样没用。

## 10. 竞争假设（待验证）

本节只保留会影响产品方向的**可证伪假设**。无一手出处的竞品名单、定价印象与厂商立场不构成决策依据，也不在现行正文保留。

**「AI 记账」本身不是差异化。** 截图解析、语音录入或对话分析都只是能力；Daybook 的差异必须落在「事后重建」的完整路径与四道可信性闸门上，而不是「用了 AI」。

**立项假设：现有工具（无论国内外）共享三个结构性局限。** 以下三条是**判断，不是核实过的事实**——它们没有逐个产品验证过，但整套产品设计建立在它们成立之上，**因此其中任何一条被证伪都值得重新看一遍 §3**：

1. **假设它们都为「当场记录」优化**，把事后重建留给用户手工完成（§1）
2. **假设语音速记止步于「更快的表单」**——说一笔、填一个表、确认一次；没有「一句话拆成多笔、跨实体、一次批量确认」这一层（§1.1）
3. **假设它们都依赖专用解析器**，因而与特定银行、支付平台或地区格式绑定。**若成立，这就不是产品的市场划分，而是解析器路线的必然结果**（§3.1）

**四道闸门不依赖竞品叙事成立。** 它们的依据是视觉模型会读错金额，而账本错误不可接受（§4）；任何竞品是否采用 AI、是否允许 AI 写入，都不改变这条产品约束。

**时间追踪**：[ActivityWatch](https://github.com/activitywatch/activitywatch)（开源、本地优先、跨平台、可写自定义 watcher）是弱信号采集的现成基础设施，**未来应接它而非自建**；它只做「自动采集」不做「人工补录」，也不碰钱——中间那层「把机器活动翻译成人类事项」正是本项目该加的价值。

**假定的结构性差异**——**这三条是推理，不是调查结论**。它们要说的是「若上述假设成立，差异就不只是包装」，而不是「已确认对手做不到」：

- 竞品的商业模式若依赖云，「本地优先」这条路对它们就是自断收入
- 竞品若自付 token 成本，就做不起重解析，只能退回专用解析器
- 竞品若是记账公司，就不会做钱与时间同轴

## 11. v2 方向：跨实体意图↔交易事实闭环（不进 v1）

待办写着「这周交房租 2000」，账单里出现一笔 2000 转账 → 待办自动打勾、预算自动核销。**意图与事实互相印证**——这是分成两个 app 做不到的事，也是「一个 app」的真正理由。

v1 只需保证数据形状（一条时间轴 + 两个实体）不挡住这条路。

## 12. 已知局限

1. **产品压缩的是整理成本，不是记录意愿。** 用户仍需在当下保留痕迹（截图、留存账单）。做不到这一步的用户，本产品救不了。
2. **事项结果依赖用户主动回溯。** Daybook 不被动观测、不把计划值、完成按钮的点击时刻或系统活动编造成实际时间；用户没有明确提供的结果仍然未知。用户口述或手工修正可以提供精确分钟或粗粒度日期范围，但其完整性取决于用户愿意补充多少。
3. **用户订阅的用量限制是真实约束。** 核心操作（多图 + 长上下文 + 多轮推理）恰好最耗额度。

### 平台风险

第三方 agent 能否使用用户的订阅额度由服务商决定，现行条款可能变化。任何依赖该能力的发布决定都必须先核实服务商的当前条款。

**2026-08-12 已核实一次，结果不是绿灯**（[01 Agent 运行时 §5](./prd/01-agent-runtime.md) R4、[spike 记录](./spikes/2026-08-12-r6-agent-runtime.md)）：当下 `claude -p` 确实仍走用户订阅额度（实测认证来源为订阅登录而非 API key），但厂商的[法务与合规文档](https://code.claude.com/docs/en/legal-and-compliance)写着 OAuth 认证「**仅面向**订阅计划购买者，用于 Claude Code 与其他原生应用的**寻常使用**」、构建产品的开发者「**应当使用 API key 认证**」；且该政策**已被改过一次又撤回**——原定 2026-06-15 起 Agent SDK 与 `claude -p` 不再计入订阅额度，当天挂出暂缓公告（[出处](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)）。**机制已经建好并上过一次膛。**

判据是：Daybook 不提供厂商登录、不打包凭证、不代理不转发（[`CLAUDE.md`](../CLAUDE.md) 约束 11 已禁这三件事），链路里没有我们的服务端，因此不构成文档所禁的「代用户路由请求」——**但这是一种读法，不是厂商的书面豁免。** 对策相应加强：可插拔后端（[ADR-0003 §4](./adr/0003-agent-runtime-and-pluggable-backend.md)）由「接口先摆着」提为**第二个实现要真能跑**。**不阻塞 M0；M4 打包发布前必须重新核实当时的条款。**

工程对策是可插拔后端接口（[ADR-0003](./adr/0003-agent-runtime-and-pluggable-backend.md)）。它只依赖「决定权在服务商手上」这一稳定事实，不依赖未经核实的历史记录，也不进入产品叙事。
